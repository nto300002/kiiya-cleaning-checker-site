# KIIYA 清掃チェッカー本番版 UI UX 実装・受け入れ TODO

## 目的と範囲

職員がアプリを操作する時間を減らし、当日の清掃と確認に集中できるようにする。作業中の記録は開いた直後から編集でき、変更は自動で残り、次に必要な操作へ迷わず進める状態を目標とする。必須の確認、作業時刻、報告内容の正確さは維持する。

この文書は [本番サイト](https://kiiya-cleaning-checker.hherocl278.chatgpt.site/) の実装要件と受け入れ条件を示す。2026-11-15公開版（Sites版 v34、ソースコミット `e412b682637e4728e3117b0f562bdd439064d9d5`）へ反映した項目も、実機・通常アカウントでの受け入れ確認が終わるまでチェックしない。実装状況と残差は [本番版との差分](./production-ux-requirements-gap-2026-11-15.md) を参照する。

## P0 作業をすぐ再開できる入口

- [ ] **当日の作業を状態に応じて開く。** ログイン・再読み込み後、当日記録の状態から入口を決める。記録がなければログインだけで空記録を作らず、開始時刻は明示的な開始操作で記録する。
  - テスト要件：記録なし、開始前、作業中、報告版作成直後、報告版作成後に再編集、日付変更後の各状態でログインと再読み込みを行う。再編集後は保存前・保存後・報告時の内容へ戻した場合も確認し、DB の記録件数、開始時刻、報告版の内容と件数を照合する。
  - 受け入れ要件：以下の入口と主ボタンに一致する。ログインだけでは記録が増えず、開始時刻も変わらない。同じ当日記録が重複しない。

  | 当日記録の状態 | 最初に表示する画面 | 主ボタンと結果 |
  | --- | --- | --- |
  | 記録なし | 本日の作業の開始画面 | 「作業を開始する」。押すと当日記録を作成して開始し、全体チェックを開く |
  | 開始前（記録あり、開始時刻なし） | 本日の作業の開始画面。入力済みの内容を保持 | 「作業を開始する」。既存記録を開始し、全体チェックを開く |
  | 作業中（開始時刻あり、報告版なし） | 全体チェック。直前の編集位置を可能な範囲で復元 | 編集欄をすぐ操作できる。次の未完了があれば「次の未完了へ」、全件完了なら「報告内容へ」 |
  | 報告版あり・現在の記録と最新版の報告内容が一致 | 報告結果と版の状態を表示。`Prepared` は「送信準備済み」と表示 | 「内容を修正して新版を作る」で全体チェックへ。画面を開いただけで再報告しない |
  | 報告版より新しい編集あり（`Prepared` のままでも判定） | 全体チェックを開き、「現在の編集は報告版に未反映」と表示。旧版の状態と現在の記録の状態を分ける | 「変更を確認して新版を作る」で報告確認へ。未完了項目があればその修正を先に促す。旧版を「現在の内容が送信準備済み」と表示しない |
  | 当日記録なし・過去の記録のみ | 新しい日付の本日の作業の開始画面 | 「作業を開始する」。過去の記録と時刻は変更しない |

  「報告版より新しい編集あり」は `status` だけで判定しない。最新報告版の `snapshot_json` と現在の `data_json` を比較した結果を API で返し、端末に未保存の変更があればそれも含めて入口と表示を決める。元の内容へ戻して両者が一致した場合は報告結果の入口に戻る。

- [ ] **スタッフと清掃範囲を全体チェック内から編集する。** 通常の作業動線から「今日の作業」「清掃範囲」への必須遷移をなくす。スタッフ、客室、人数、作業種別、トイレ・シャワー数は必要なときだけ開く編集領域にまとめる。
  - テスト要件：各項目の変更直後にチェックへ戻る操作なしで作業を続ける。人数や作業種別の変更で再確認が必要な項目だけが適切に戻ることを確かめる。
  - 受け入れ要件：作業開始後の基本動線は「全体チェック → 報告確認」。必須項目と報告前確認は省略されない。

## P1 チェック画面で探す操作を減らす

- [ ] **次の未完了項目へ直接移動する。** 未完了一覧と進捗付近に、対象の客室・作業カード・休憩回答を開いて移動する導線を置く。現行の「次の未完了へ」が最初の項目にしか進まず、一部の項目で対応する入力欄へ移動できない動きも改める。
  - テスト要件：客室、各ユニットの作業、シャワー実施数、休憩回答をそれぞれ唯一の未完了項目にしたケースと、全件完了のケースを確認する。
  - 受け入れ要件：どの未完了項目にも 1 タップで到達できる。移動だけで項目が完了扱いにならず、全件完了時に無効な導線が残らない。

- [ ] **進捗と未完了数を統一する。** 「0/12」「未完了14件」「13箇所未入力」のように異なる数を同時に出さず、同じ判定から表示する。報告を止めている理由は項目名で示す。
  - テスト要件：客室の追加・削除、チェック、担当者、シャワー実施数、休憩回答の変更前後で件数と報告可否を照合する。
  - 受け入れ要件：同じ画面に矛盾する件数が出ない。報告できない場合、次に直す項目が分かる。

- [ ] **担当者をまとめて割り当てる。** 当日のスタッフから複数の作業に一括で担当者を割り当て、例外の作業だけ個別変更できるようにする。担当者の自動確定は行わず、一括割当は未設定・未開始の作業だけに適用する。
  - テスト要件：スタッフ 1 人・複数人、一括割当後の個別変更、一括割当の再実行、開始済み作業を含む状態、作業対象変更後、再読み込み後を確認する。
  - 受け入れ要件：同じ担当者を作業ごとに繰り返し選ぶ必要がない。再実行しても個別変更済み・開始済みの担当者を上書きしない。明示的に割り当てる前に誤った担当者が記録されず、開始・完了時刻も維持する。

## P2 周辺操作と表示を整理する

- [ ] **履歴へ直接移動する。** 作業画面から設定を経由せずに履歴を開き、戻ると元の作業位置を復元する。
  - テスト要件：チェック途中と報告確認途中から履歴を開き、戻った際の画面、スクロール位置、入力内容を確認する。
  - 受け入れ要件：履歴へ 1 タップで移動でき、戻った後に作業箇所を探し直さない。

- [ ] **常時表示する情報を減らす。** 通常の保存成功通知、作業中に影響しない Chatwork 連携案内、利用できない報告形式や送信状態を整理する。保存失敗、競合、報告不能は対応方法とともに表示する。
  - テスト要件：通常作業、通信失敗、更新競合、報告確認、Chatwork 設定が必要な場面を確認する。
  - 受け入れ要件：通常時は作業に必要な情報が優先され、対応が必要な例外だけが目立つ。利用できない選択肢で操作が止まらない。

## 横断要件

- [ ] **自動保存の信頼性を確認し、失敗時の再送を実装する。**
  - テスト要件：入力直後の画面終了と再起動、オフラインからの復帰、サーバーエラー、別画面・別端末からの同時更新を確認する。同時更新では共通の保存済み版から端末 A・B が別項目を変更した場合、同じ項目を異なる値にした場合、片方が削除した項目をもう片方が編集した場合を試す。別項目の例として、一方が客室の人数・作業種別・清掃対象を変更し、もう一方が変更前の条件で客室確認や作業完了を記録する各ケースを含める。統合後の未完了項目と報告可否を確認し、影響のない客室の確認は残ることも確かめる。競合解決中の再読み込みと、解決直前の再競合も確認する。
  - 受け入れ要件：通常時は入力を自動で保存し、「未保存」案内や手動保存操作を要求しない。通信失敗時も端末の入力を保持し、復旧後に再送できる。競合時は共通の保存済み版・最新サーバー版・端末入力の 3 版を比較する。端末で変更していない項目は最新サーバー版を保持し、変更箇所が重ならなければ両方の変更を統合する。ただし保存前に統合結果を業務ルールで再検証し、人数・作業種別・清掃対象が変わった条件の下で行われた客室確認・職員最終確認・作業完了は、必要な範囲だけ未確認に戻す。画面の未完了数と報告可否も再計算し、再確認が終わるまで報告を確定できない。同じ項目への異なる変更や削除と編集の衝突は表示し、利用者が項目ごとに残す値を選ぶ。端末入力とサーバー版は選択が終わるまで保持する。統合した内容を最新の更新番号で保存し、再競合したら新しいサーバー版を取得して 3 版比較と再検証をやり直す。端末のデータ全体を最新サーバー版へ上書き保存しない。

- [ ] **通常アカウントの権限を以前の要件に合わせる。** 通常アカウントも自分の作業の作成・編集・報告と日常操作を利用できるようにする。Chatwork のルーム ID 登録とマスタ変更は制限する。画面と API の両方を下表に合わせる。
  - テスト要件：下表の各行について通常アカウント・現場職員・アプリ管理者で UI 操作と直接 API 呼び出しを確認する。許可は成功、拒否は 403 とデータ不変を確認する。他職員の記録 ID、他職員・本人の職員 ID、古い更新番号を指定した場合も確認する。表示名変更後に新しい報告版で使う担当者名と、既存の確定済み報告版が変わらないことを確認する。
  - 受け入れ要件：通常アカウントで自分の日常作業が完了でき、閲覧・編集の境界が UI と API で一致する。制限対象は直接 API を呼んでも実行できない。権限変更によって制限を回避できない。

  | 画面操作 | 対応する API | 通常 | 現場職員 | アプリ管理者 |
  | --- | --- | --- | --- | --- |
  | 本日の作業・履歴一覧を見る | `GET /api/works` | 許可 | 許可 | 許可 |
  | 自分・他職員の記録、画像、報告版を見る | `GET /api/works/:id`、`GET /api/works/:id/images/:imageId`、`GET /api/works/:id/reports/:reportId/markdown` | 許可 | 許可 | 許可 |
  | 自分の作業を作成・開始・編集・報告する | `POST /api/works`、`PUT /api/works/:id`、`POST /api/works/:id/start`、`GET /api/works/:id/preview`、`POST /api/works/:id/press`、`POST /api/works/:id/reports` | 許可 | 許可 | 許可 |
  | 自分の記録に画像を追加する | `POST /api/works/:id/images` | 許可 | 許可 | 許可 |
  | 他職員の記録を編集・開始・報告・画像追加する | 上記の更新系 `/api/works/:id...` | 拒否 | 拒否 | 拒否 |
  | 職員台帳を閲覧する | `GET /api/users` | 許可 | 許可 | 許可 |
  | 自分の表示名を変更する | `PUT /api/users/:自分のid/display-name` | 許可 | 許可 | 許可 |
  | 他職員の表示名を変更する | `PUT /api/users/:他職員のid/display-name` | 拒否 | 許可 | 許可 |
  | 職員の利用登録・権限変更をする | `GET /api/users/registration-candidate/:id`、`PUT /api/users/registration-candidate/:id/display-name`、`POST /api/users`、`PUT /api/users/:id/role` | 拒否 | 拒否 | 許可 |
  | Chatwork の接続アカウントを設定・確認する | `GET /api/chatwork/production/settings`、`POST /api/chatwork/production/oauth/start`、`GET /api/chatwork/production/oauth/callback`、`POST /api/chatwork/production/account/confirm` | 許可 | 許可 | 許可 |
  | Chatwork のルーム ID を登録・確定する | `POST /api/chatwork/production/room/preview`、`POST /api/chatwork/production/room/confirm` | 拒否 | 許可 | 許可 |
  | マスタを閲覧する | `GET /api/master` | 許可 | 許可 | 許可 |
  | マスタ変更を申請する | `POST /api/master/changes` | 拒否 | 許可 | 許可 |

  権限変更はルーム ID 登録・マスタ変更への昇格経路になるため、利用登録とともにアプリ管理者だけが実行する。本番版の権限変更もこの境界を維持する。通常アカウントが変更できる表示名は本人のものだけとし、`GET /api/users` では本人の ID・更新番号を返しても、他職員の更新用情報は返さない。氏名以外の内部情報も返さない。既存の他職員記録は閲覧のみとする。これらの権限範囲は本番運用担当者と照合して受け入れを確定する。

## 完了判定

- [ ] スマートフォン幅を中心に、記録なしから報告確認までの一連の作業を通す。狭い画面でも主要操作が隠れず、キーボードとスクリーンリーダーで未完了項目へ到達できる。
- [ ] 既存の人数・宿泊なし判定、清掃対象変更時の再確認、不備、作業時刻、報告内容に回帰がないことをテストする。
- [ ] 本番版ソースのビルドと関連テストを通し、現場職員と通常アカウントの両方で受け入れ要件を確認する。検証では実データを無断で変更しない。
- [ ] 同じ当日記録・同じスマートフォン幅で変更前後の操作数を記録する。作業中の再開から最初の入力欄の表示まで **0 タップ**、最初の入力操作まで **1 タップ以内**、未完了項目への移動 **1 タップ以内**、10 作業に同じ担当者を付ける場合は **担当者選択と一括適用の計 2 操作以内**を受け入れ目標とする。例外の個別変更は別に数え、画面遷移数も併記する。
