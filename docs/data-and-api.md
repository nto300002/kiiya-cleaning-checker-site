# D1・R2・API移行設計

## データの対応

[元の論理データ設計](baseline/data-design.md)の業務エンティティと版・履歴の意味を保持し、物理DBだけをD1向けに再設計する。`AppUser`、`MasterRevision`、`WorkRecord`、`WorkTaskProgress`、`RoomDefect`、`ReportVersion`、送信成果物、通知試行、冪等キー、結果不明の証跡、期限処理の状態を個別に識別する。大きなJSONを1行へ保存する場合も、作業ID・作成者・日付・版番号・状態・期限・外部投稿IDは検索可能な列として持つ。

- 作業更新は`revision`と`stateVersion`の条件付き更新で競合を検出する。報告版の確定と作業状態、版番号、冪等キーの記録は原子的に扱う。D1の具体的なトランザクション手段を先に検証し、途中失敗で版と作業が食い違わないことを試験する。
- マスタ確認時は元版、同日0時の予約競合、編集者と確認者の分離を同時に判定する。不変の予約版・確認記録は取下げ後も監査用に残す。
- 日付の判定は`Asia/Tokyo`の作業日と適用日で行う。DBの保存時刻はUTCとして保持し、表示時に変換する。
- R2には`works/<workId>/<imageId>`、`reports/<reportId>/report.<pdf|md>`のように固定IDで保存する。作業側で画像を外しても報告版が参照する元画像は必要期間保持する。アップロード時は同一キーの再利用を拒否する。
- 報告ファイルをR2へ先に書いた後でDB確定が失敗した場合は、確定状態を照会して不要な生成物を削除する。DB照会も不能なら保留し、日次処理が古い孤立ファイルをR2一覧とDBの報告IDの一括照合で回収する。ページ処理、実測時間、削除失敗時の再実行を検証する。
- 未送信内容の7日後消去、送信済み版の無期限保持、結果不明時の保留は元設計どおり。削除対象にはR2の画像・生成物とD1の本文・スナップショットを含め、保持すべき版番号・結果不明の証跡は残す。

## API契約

[元のAPI設計](baseline/api-design.md)を業務操作の出発点とする。パス・要求・応答を新しいOpenAPIとして再作成し、認証ヘッダー、エラー、プレビュー、報告版、画像、不備、マスタ変更、履歴をSitesのサーバールートに合わせて定義する。元OpenAPIをそのまま採用済みと表示しない。

| 操作群 | 維持する外部契約の要点 |
| --- | --- |
| 認証・職員 | 401/403/404を区別し、全職員閲覧と作成者更新をサーバーで強制。IT権限を別に判定 |
| マスタ | 作業日で有効版を取得。開始済み作業の版は固定。通知成功だけでは適用しない |
| 作業・チェック | 10作業の`workTasks`、対象室のサーバー導出、種別別回答、修正前後履歴、対象ゼロ件の判定 |
| 画像 | アップロード・認可付き参照・除外。R2キーと画像IDの再利用を拒否 |
| 報告 | プレビューと初回押下を区別。確定時に再検証し版番号・本文・画像参照を固定 |
| 配信 | `202`は受付のみ。成果物すべての投稿確認で`Sent`、不確実なら`Unknown`。既投稿を調べるまで自動再送しない |
| 期限・履歴 | 7日消去と無期限保持を分け、旧報告版の写しを維持 |

### 専用ワーカー用の内部契約（案A）

Cloud Tasks／Schedulerは認証付きでCloud Runワーカーを呼ぶ。ワーカーからSiteへの呼出しは職員向けAPIと分け、サービス認証、ジョブ種別・対象ID・リースの検査を必須とする。Sitesのサービスアクセス方式と失効方法を実環境で確かめ、成立する方式をSites版OpenAPIへ固定する。下表は契約対象であり、パスと要求・応答の確定はIssue #3で行う。

| 操作 | 制約・結果 |
| --- | --- |
| ジョブ確保 | 報告・通知・照合・期限処理の対象を条件付きで確保し、リースID、期限、版ID、固定済み成果物一覧を返す。重複配送には同一結果または競合を返す |
| 成果物取得 | 確保済みジョブが参照するR2ファイルだけを認可付きで転送する。サイズ・ハッシュ・期限を照合し、任意キーの取得を許さない |
| 投稿用トークン取得 | 有効な投稿ジョブのリースに限りSite側が必要なら更新し、アクセストークンと有効期限を返す。リフレッシュトークンと暗号化鍵は返さない。応答・中継ログをキャッシュしない |
| 結果保存・状態照会 | 成果物ごとの投稿ID・ファイルID・結果をリースと状態版で条件付き保存する。応答喪失時は現在状態を照会し、既投稿または結果不明を無条件に再送しない |

期限処理のD1/R2一覧・削除もSiteの内部API経由で行う。大件数時はページ単位の進捗と再開位置をD1に持ち、Cloud RunからD1/R2へ直接接続しない。

## 既存データ

実データ移行は[所有者対応手順](owner-mapping.md)と職員権限を確定した後に行う。PostgreSQLからのエクスポート、D1への再投入、Cloud StorageからR2への非公開ファイル複写、件数・ハッシュ・版参照の照合、切替時の書き込み停止と復旧手順を設計する。旧形式の箇所別時刻や「洗面周り床」を新10作業へ推測で転記しない。送信済み報告は元の写しを保持する。未確定所有者の作業を他職員へ自動で割り当てない。
