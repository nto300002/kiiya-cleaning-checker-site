# Chatwork連携の画面・配信契約（案A）

## 接続試験と本番設定

Issue #10は**既存の本番Site内で行う期限付き試験**であり、独立した検証用Siteではない。サーバーの環境ゲートと`chatwork_smoke`名前空間を使い、固定した検証用ルームにのみSiteからテスト本文を投稿する。この成功はOAuth接続と検証用ルームの投稿を示すだけで、本番報告の送信設定を`DestinationVerified`にしない。

本番設定を`DestinationVerified`（送信先確認済み）にするには、`manage_chatwork`権限の設定担当職員が送信元`account_id`を確認し、業務報告用room IDとルーム名を確定し、その**業務報告ルームへの投稿権限**を別途確認する。ルーム情報取得だけでは投稿権限を証明できないため、テスト投稿の投稿IDとChatwork上の表示を照合する。この状態だけでは職員の本番送信ボタンを有効にしない。Cloud Runワーカー、キュー、Site内部API、成果物・結果保存経路をIssue #5・#9で受け入れ、配備版の実行可否をサーバーが確認したときだけ`DeliveryEnabled`（報告送信可）とする。統合受け入れ中の実投稿はIT担当者が管理する限定経路で行う。

本番room IDは、プログラミングを要しない設定画面で専用の`manage_chatwork`権限を持つ設定担当職員が入力する。APIで取得したルーム名を表示し、本人が確認してからDBの本番送信設定へ保存する。OAuth接続は投稿元アカウントの認可であり、room IDの入力だけでは接続・送信を有効にしない。本番room IDを環境変数・ソースコード・公開Issueへ記録しない。Issue #10の検証用固定room IDは別設定のままとする。

本番用の設定APIの要求・応答、状態、競合条件は[本番Chatwork送信設定API契約](chatwork-production-settings-api.md)に定める。

## 画面と権限

| 画面 | Chatwork設定担当職員 | その他の職員 | サーバーAPI |
| --- | --- | --- | --- |
| 最初の画面 | 本番room IDが未設定なら設定手順と「Chatwork連携を設定」導線を表示。ルーム名の確認と設定画面へ進む | 本番room IDが未設定なら「送信先の設定が必要です。設定担当職員に連絡してください」と表示。清掃記録は続けられる | 読み取りAPIが`RoomNotConfigured`等の設定状態だけを返し、room IDは返さない。状態取得失敗は未設定と断定しない |
| 設定 > Chatwork連携 | OAuth接続、送信元ID確認、room ID入力・ルーム名確認、テスト投稿、再接続、宛先再確認。状態・最終確認時刻を表示 | 連携欄と操作を表示しない。設定内のアーカイブ導線などは通常どおり利用できる | 接続状態の詳細取得・変更・試験投稿は`manage_chatwork`を毎回検査 |
| 報告確認 | 確定済み送信元名・送信先ルーム名と利用状態を表示 | 同じ表示用情報を読める。送信元・room IDは変更できない | 報告向け読み取りAPIは確認済みの表示名・ルーム名・利用可否・不透明な設定版だけを返し、`account_id`・room ID・トークン・試験設定を返さない |
| 報告結果 | 送信待ち、送信済み、失敗、結果不明、設定変更による保留、期限切れを表示 | 自分の報告の状態と必要な対応を確認 | `202`は受付だけ。必須成果物の投稿確認後に`Sent` |

本番設定の状態は`Unconfigured`、`Disconnected`、`AccountConfirmationRequired`、`DestinationVerificationRequired`、`DestinationVerified`、`ReconnectRequired`とし、変更処理中は別に`ChangePending`を示す。`DeliveryEnabled`は送信先確認、承認済み配備版・運用有効化、直近3分以内の認証済みワーカーハートビートを合わせた計算結果である。ワーカー停止・手動停止時は通常報告と確認専用投稿の新規POSTを拒否する。手動停止の解除は送信先未確認でも経路が正常なら可能とし、通常報告は人による本番roomの投稿照合まで禁止する。設定画面全体を制限せず、Chatwork連携欄と変更APIを`manage_chatwork`に限定する。画面の非表示だけに依存せず、権限のない職員が直接変更APIを呼んでも403にする。

最初の画面は本番送信設定のサーバー応答を読み、room ID未設定を最優先で案内する。未設定でも作業記録・報告プレビューを止めず、本番送信だけを無効にする。`manage_chatwork`保有者には入力画面へのボタン、その他の職員には設定担当職員への連絡案内を出す。設定後は最新状態を読み直して案内を消す。通信失敗時は「設定状態を確認できません」と表示し、未設定・送信可能のどちらにも推定しない。

## 報告確定と送信登録

1. 作成者だけが報告を確定する。確定APIは内容・版番号を固定し、冪等キーとともに報告IDを返す。同じキーと同じ内容の再操作は同じ報告IDを返し、異なる内容は競合とする。
2. 作成者だけが、その報告IDに対して送信登録APIを呼べる。報告版だけが作成され送信登録に失敗した場合、同じ報告IDから再試行できる。同一報告IDの重複要求は既存の送信ジョブを返し、二重にジョブを作らない。結果不明の投稿を再操作だけで自動再送しない。
3. 送信登録APIには報告確認画面で得た不透明な設定版を送る。サーバーで現行版と一致しない場合は409を返し、画面に新しい送信先を再表示して作成者の再確認を求める。一致時に**本番設定版・送信元`account_id`・宛先room ID**をジョブへ固定する。リクエストから任意の送信元・room IDを受け付けず、サーバーが確定済み設定から導出する。トークン更新番号は設定版と分け、通常のトークン更新だけではジョブを保留しない。
4. ワーカーは投稿開始時と**各成果物の投稿直前**に、ジョブの設定版・送信元・宛先と現行の`DeliveryEnabled`設定を照合する。設定変更は進行中の投稿リースを尊重し、外部API呼出し中の1成果物は結果記録または`Unknown`判定まで待つ。変更後は次の成果物を投稿しない。本文を送った後で画像を送る前に変更された場合も、既投稿の`message_id`・ファイルIDと固定宛先を残し、未投稿成果物を`ConfigurationChangedHold`として保留する。同一報告版の成果物を新ルームへ振り替えず、`Sent`にも進めない。
5. 保留の再確認には旧・新の宛先、既投稿ID、残りの成果物、変更履歴をIT担当者と作成者に示す。同一送信元・同一宛先をIT担当者が再確認した場合だけ、既投稿の照合後に監査履歴を残してジョブの確認済み設定版を条件付き更新し、**未投稿成果物だけ**元のルームへ送って再開する。宛先・送信元が変わる場合は元ジョブの残りを送らない。元ジョブを終える操作と新版作成の条件は次節に定める。元ジョブの既投稿IDを消したり、自動で投稿を取り消したりしない。

### 旧ジョブの手動終了

元の送信元・宛先で続けないと決めた場合、**IT担当者**が旧ルームの既投稿IDと全成果物の結果を照合し、`ConfigurationChangedHold`を`Failed`（理由`PartialDeliveryStoppedByDestinationChange`）に手動確定する。`Unknown`が生じていた場合も、投稿の有無を照合して判定不能がなくなってから同じ理由で`Failed`へ確定する。確定記録には報告ID・版番号、既投稿IDと元のroom ID、未投稿成果物、確認者Site ID・確認日時、旧ルームの既投稿内容への対処を残す。全成果物が揃わない旧版は`Sent`にしない。投稿の成否が1件でも判定不能なら`Unknown`を維持し、`Failed`へ確定しない。IT担当者の確定後、作成者が新しい宛先を確認して**新しい報告版**を作る。旧ジョブは再開・再登録できず、既投稿を自動削除しない。

設定変更要求と成果物投稿はD1の状態版・短期リースで調停する。初期の成果物リースは5分、外部POSTのタイムアウトは4分以下とし、実測後に受け入れ前の設定値を固定する。外部API呼出し中なら変更要求を保留し、その成果物の投稿結果を記録するか`Unknown`へ確定した後に設定版を進める。変更待ちの間は次の成果物の投稿リースを発行しない。設定変更APIの受付応答を変更完了と表示せず、完了状態を読み直す。

受け入れ時は、代表的な本文・画像入りPDF・複数画像・Markdown添付について、**リース取得から結果のD1確定保存まで**を実測する。R2取得、必要なトークン更新、Chatwork POST、応答処理、D1保存を含め、POST単体の時間も分けて記録する。各構成を少なくとも3回実行し、ネットワーク遅延とD1保存遅延を加えたケースも各1回以上測る。初期設定での合格条件は、各POSTが4分以内、成功した各成果物の全工程が4分30秒以内（5分リースに30秒以上の余裕）で、通常成功をリース失効による`Unknown`にしないこと。超過または余裕不足ならリース・タイムアウトと実行基盤を見直して再実測し、調整後も全工程からリース満了まで30秒以上の余裕を確保した最終値と最大所要時間を受け入れ記録に固定する。結果不明へ安全に遷移したことだけで性能ケースを合格にしない。

ワーカーが停止して結果を保存しない場合、**毎分の監視処理**がリース期限切れを検出し、D1の状態版とリースIDを条件に対象成果物を`Unknown`へ遷移させ、旧宛先・投稿試行時刻・確認待ちの証跡を残す。この遷移が済んだら待機中の設定変更を進められるが、旧ジョブの残りは投稿しない。遅れて戻った旧リースの結果更新は拒否する。`Unknown`は既投稿の可能性を含むため、自動再送せずIT担当者が旧ルームを照合する。監視停止時は復帰後の最初の実行で期限切れを処理し、設定変更要求を無期限に待たせない。

### 設定変更による保留と保存期限

- **既投稿成果物が0件**の`ConfigurationChangedHold`は、初回報告ボタン押下から7日後まで再開可能とする。期限到来時に`Expired`へ確定し、本文・固定画像参照・未送信成果物を期限処理で削除する。期限後は旧ジョブを再開せず、報告ID・版番号・保留・期限切れの監査記録だけ残す。
- **既投稿成果物が1件以上、または投稿成否が不明**の保留は`Sending`／`Unknown`と同じく、結果確定まで本文・画像・成果物を保持する。7日経過時はIT担当者へ要対応として通知し、自動削除しない。全成果物の結果が確認されて手動で`Sent`と確定した版は無期限保持する。部分送信を`Failed`と確定した版は未送信確定の期限規則へ戻し、元の7日期限が過ぎていれば直後の期限処理で内容を削除する。既投稿IDと判断履歴は残す。
- 日次処理は保留の既投稿件数と`Unknown`の有無を確認し、削除・保持のどちらを選んだか記録する。削除と手動再開は状態版を条件に競合を防ぎ、削除済み成果物を使う再開を拒否する。

## 案Aの内部API境界

本番設定と報告向け読み取りのパス・要求・応答は[設定API契約](chatwork-production-settings-api.md)を基準とする。報告・ワーカー内部APIのパスは仮名で、全体のOpenAPIへの統合はIssue #3で行う。

| 操作 | 仮のアプリAPI | 条件 |
| --- | --- | --- |
| 本番接続開始・コールバック | `POST /api/chatwork/production/oauth/start`、`GET /api/chatwork/production/oauth/callback` | `manage_chatwork`権限、state/PKCE、サーバー側トークン保存。試験用OAuth経路から分離 |
| 本番送信元・送信先の確定 | `POST /api/chatwork/production/account/confirm`、`POST /api/chatwork/production/room/preview`、`POST /api/chatwork/production/room/confirm`、`GET /api/chatwork/production/changes/{changeId}` | `manage_chatwork`権限、候補の本人・期限・設定版を検査。`202`の保留は完了照会まで成功扱いにしない |
| Issue #10の接続試験投稿 | `POST /api/chatwork/smoke/test-message` | IT権限、期限・環境ゲート。`chatwork_smoke`設定とサーバー側の固定検証ルームだけを参照し、本番設定を更新しない |
| 業務報告ルームの権限確認 | `POST /api/chatwork/production/verify-posting`、`GET /api/chatwork/production/verifications/{id}`、`POST /api/chatwork/production/verifications/{id}/confirm` | `manage_chatwork`権限、ジョブの設定版・送信元・宛先を投稿直前と確認確定時に照合。成功した投稿ID・ルーム名を人が照合した後に`DestinationVerified`とする |
| 報告向け表示 | `GET /api/report-delivery-settings` | 有効職員には`setupRequired`と`setupReason`（例: `RoomNotConfigured`）、確認済み送信元名・ルーム名・`DeliveryEnabled`可否・不透明な設定版のみ。room ID・トークンを返さない。設定詳細APIはIT限定 |
| 報告確定・送信登録・状態 | `POST /api/works/{workId}/reports`、`POST /api/works/{workId}/reports/{reportId}/send`、`GET /api/works/{workId}/reports/{reportId}` | 確定・登録は作成者のみ。登録時に画面で確認した設定版を照合。送信登録の成功応答は受付状態、結果取得は既存の閲覧権限に従う |
| ワーカーのジョブ確保・成果物取得・トークン取得・結果保存 | 認証付き内部API | サービス認証と短期リースを検査。各成果物の投稿直前に固定設定と現行設定を照合し、既投稿IDを維持する |

ワーカーへ渡すのはChatworkの**通常のアクセストークン**であり、ジョブ専用にChatwork側の権限を縮めたものではない。内部APIは有効なジョブID・短期リース・サービス認証を要し、ワーカーはトークンを実行中のメモリだけで扱う。タスク本文、通常ログ、永続ストレージ、結果APIへ残さない。リフレッシュトークンの取得と更新はSite側だけが行う。401ではSite側の更新可否を確認し、更新不能なら再接続を求める。403では宛先・権限を再確認し、投稿成否が不明なら`Unknown`として照合する。
