# Sites構成と移行境界

## 採用方針（案A）

Siteを職員向け画面・業務API・D1/R2の正本とし、Cloud Run専用ワーカーをChatwork投稿と定期・遅延処理の実行者にする。Cloud Tasksは個別配送と5分後照合、Cloud Schedulerは毎分監視と日次期限処理を起動する。これは構成の選択であり、Siteとワーカーの実接続や本番切替が完了した意味ではない。

## 構成の対応

| 現行の設計 | 案Aでの担当 | 検証条件 |
| --- | --- | --- |
| Firebase HostingのReact PWA | SitesのVinext/Worker画面 | スマートフォン表示、既存画面フロー、オフライン入力、カメラ・画像選択を実機確認 |
| Cloud Run API・非公開ワーカー | Sitesのサーバールート／WorkerとCloud Run専用ワーカー | Siteが認証・認可、データ管理、PDF生成を担当。専用ワーカーがChatwork投稿を担当し、それぞれの実行限界を検証 |
| Cloud SQL for PostgreSQL | SitesのD1 | 制約、版固定、競合更新、冪等性、複数書き込みの整合、復元方法を検証 |
| 非公開Cloud Storage | SitesのR2 | 画像・報告ファイルの非公開参照、一覧・削除、保存期限、容量を検証 |
| Secret Manager | Sitesのホスト済みシークレット＋D1の暗号化されたトークン記録 | 固定のOAuthクライアント秘密値・暗号化鍵と、実行中に更新されるトークンを分離して検証 |
| Cloud Tasks・Cloud Scheduler・Cloud Run Jobs | Cloud Tasks・Cloud SchedulerからCloud Run専用ワーカーを起動 | 1分監視、5分照合、日次期限処理、認証、再配信・重複防止を実測 |
| Google IDトークンと職員台帳 | SitesのサインインIDと職員台帳。共通アカウントを避ける運用は人が担当 | IT権限、利用停止、全職員閲覧、既存Google IDからの移行を確認 |

SitesのWorkerはCloudflare Workers上で動き、HTTPによる外部接続が前提で、raw TCPは使えない。したがって現行のPostgreSQLドライバーとGCPメタデータ認証を移植せず、D1/R2とSitesの認証・シークレットに合わせて作り直す。Site用のD1/R2はホスティング設定の論理バインディングとして宣言し、資格情報をソースへ置かない。

## 公開範囲と認可

GitHubリポジトリがpublicでも、作業データを載せるSiteは職員限定を前提とする。Siteの公開範囲と認証方法は別途確定する。職員ごとのChatGPTアカウント利用を人の運用で徹底し、共通アカウントの検知・禁止機能はMVPに設けない。ただしアプリはサインイン情報だけで職員資格を認めず、サーバー側の`AppUser`有効状態と権限を毎回確認する。公開アクセスを選ぶ場合も匿名APIには記録・画像・報告・設定を返さない。画像は公開URLを発行せず、認可付きのサーバールートから返す。共通アカウントが使われると実際の操作者を識別できないことは運用上の残存リスクとして記録する。

## Chatworkと非同期処理

ChatworkのOAuth認可コード、state/PKCE、トークン保存・更新とルーム名確認はSite側Workerが担当する。本文・PDF・画像の投稿と投稿照合はCloud Run専用ワーカーが担当し、成果物別の結果は保護されたSite APIを通じD1へ保存する。外部投稿とD1更新は同一トランザクションにできないため、既投稿照合、`Unknown`、手動確定、冪等な処理を維持する。

OAuth接続は職員個人ではなく、環境ごとに1件のアプリ送信設定へ既存Chatworkアカウント1件を結び付ける。`manage_chatwork`権限の設定担当職員が`GET /me`の`account_id`と表示名を確認して固定し、送信先ルームをAPIで照合する。すべての自動報告はそのアカウント名義で送り、作業・報告の操作者はSitesの職員IDを本文と履歴に別途記録する。一般職員にはChatworkログインを求めない。

既存の本番Site内で行うIssue #10の期限付き・検証用ルーム試験は、本番送信の有効化とは分ける。本番の業務報告ルームで投稿権限を確認した状態は送信先確認済みであり、職員の報告送信可否はCloud Run・キュー・内部APIの受け入れ結果も条件にする。報告ジョブには作成者が確認した設定版・送信元ID・宛先IDを固定し、各成果物の投稿直前に設定が変わっていれば既投稿IDを残して残りを保留する。設定・報告画面と再開・期限条件は[画面・配信契約](chatwork-screen-and-delivery.md)に定める。

OAuthクライアント秘密値とトークン暗号化鍵はSitesのホスト済みシークレットに置く。Site側Workerが取得・更新するアクセストークンとリフレッシュトークンは暗号化してD1に保存する。Cloud Runワーカーは更新トークンを取得せず、確保済みジョブに限って保護されたSite APIから投稿用アクセストークンを取得し、実行中のメモリでだけ扱う。初回保存、同時更新、暗号化鍵の更新、再接続と内部APIの制約は[トークン設計](chatwork-token-storage.md)で定める。

Sitesの公式資料からは既存要件の1分監視と報告ごとの5分後実行を保証する仕様を確認できない。[調査記録](sites-async-review.md)を参照する。Cloud Tasks／SchedulerはCloud Run専用ワーカーを認証付きで呼び、ワーカーが保護されたSite APIへ接続する。外部実行者に一般職員の権限を与えず、接続・遅延・重複配送を実測するまで統合受け入れを完了にしない。

### Siteと専用ワーカーの境界

Cloud Runワーカーは保護されたSite APIだけを通じてジョブを確保し、固定済み報告版・必要なファイル・投稿用アクセストークンを取得し、成果物ごとの投稿結果を返す。D1・R2には直接接続しない。Site APIはジョブ種別、対象ID、リース、状態遷移、ファイル参照を制限し、Sitesのサービスアクセスまたは検証済みの専用認証で外部呼出しを検査する。サービスアクセスは職員本人のIDを与えない。アクセストークンとファイルの転送量、タイムアウト、重複配送時の排他は小さな実証で確認する。内部APIの契約は[API移行設計](data-and-api.md)に記す。

案Aの認証・ファイル転送・状態更新が実証で成立しない場合は採用判断を再審議する。代替案BはGCP側をDB・ファイルの正本、Sitesを画面配信に限る構成であり、現時点では採用しない。案を切り替える際は受け入れケースを改訂し、同じ記録を両DBで別々に更新しない。判断と検証結果は[Issue #6](https://github.com/nto300002/kiiya-cleaning-checker-site/issues/6)に記録する。

## 移行しないもの

元リポジトリのGCP実リソース、既存PostgreSQL、Cloud Storageオブジェクト、Chatworkトークンをこの公開リポジトリへ複写しない。元の稼働系を切り替える作業も、この設計案の作成には含めない。
