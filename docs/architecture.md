# Sites構成と移行境界

## 候補構成

| 現行の設計 | Sites版の候補 | 検証条件 |
| --- | --- | --- |
| Firebase HostingのReact PWA | SitesのVinext/Worker画面 | スマートフォン表示、既存画面フロー、オフライン入力、カメラ・画像選択を実機確認 |
| Cloud Run API・非公開ワーカー | Sitesのサーバールート／Worker | 認証・認可、PDF生成、Chatwork HTTP通信、処理時間とメモリを検証 |
| Cloud SQL for PostgreSQL | SitesのD1 | 制約、版固定、競合更新、冪等性、複数書き込みの整合、復元方法を検証 |
| 非公開Cloud Storage | SitesのR2 | 画像・報告ファイルの非公開参照、一覧・削除、保存期限、容量を検証 |
| Secret Manager | Sitesのホスト済みシークレット＋D1の暗号化されたトークン記録 | 固定のOAuthクライアント秘密値・暗号化鍵と、実行中に更新されるトークンを分離して検証 |
| Cloud Tasks・Cloud Scheduler・Cloud Run Jobs | Sitesの定期更新を調査し、不足する遅延・定期処理にはCloud TasksとCloud Schedulerを使う候補 | 1分監視、5分照合、日次期限処理、認証、再配信・重複防止を実測 |
| Google IDトークンと職員台帳 | SitesのサインインIDと職員台帳。共通アカウントを避ける運用は人が担当 | IT権限、利用停止、全職員閲覧、既存Google IDからの移行を確認 |

SitesのWorkerはCloudflare Workers上で動き、HTTPによる外部接続が前提で、raw TCPは使えない。したがって現行のPostgreSQLドライバーとGCPメタデータ認証を移植せず、D1/R2とSitesの認証・シークレットに合わせて作り直す。Site用のD1/R2はホスティング設定の論理バインディングとして宣言し、資格情報をソースへ置かない。

## 公開範囲と認可

GitHubリポジトリがpublicでも、作業データを載せるSiteは職員限定を前提とする。Siteの公開範囲と認証方法は別途確定する。職員ごとのChatGPTアカウント利用を人の運用で徹底し、共通アカウントの検知・禁止機能はMVPに設けない。ただしアプリはサインイン情報だけで職員資格を認めず、サーバー側の`AppUser`有効状態と権限を毎回確認する。公開アクセスを選ぶ場合も匿名APIには記録・画像・報告・設定を返さない。画像は公開URLを発行せず、認可付きのサーバールートから返す。共通アカウントが使われると実際の操作者を識別できないことは運用上の残存リスクとして記録する。

## Chatworkと非同期処理

ChatworkのOAuth認可コード、state/PKCE、ルーム名確認、本文・PDF・画像投稿はWorkerからのHTTP通信を候補とする。投稿後の状態は成果物ごとに保存する。外部投稿とD1更新は同一トランザクションにできないため、既投稿照合、`Unknown`、手動確定、冪等な処理を維持する。

OAuthクライアント秘密値とトークン暗号化鍵はSitesのホスト済みシークレットに置く。**Workerが取得・更新するアクセストークンとリフレッシュトークンは、暗号化してD1に保存する候補**とし、初回保存、同時更新、暗号化鍵の更新、再接続を[トークン設計](chatwork-token-storage.md)で定める。ホスト済みシークレットをWorkerから書き換えられる保存先とは扱わない。

Sitesの公式資料は公開Siteのクラウド定期更新を説明するが、既存要件の1分監視と報告ごとの5分後実行を保証する仕様は確認できない。[調査記録](sites-async-review.md)を参照する。このため、5分後の個別照合と非同期投稿には**Cloud Tasks**、毎分監視と日次期限処理には**Cloud Scheduler**を代替候補とする。Cloud Tasksだけでは繰り返し日次実行を前提にしない。いずれも認証済みのSite実行入口を安全に呼べるか、Sitesのサービスアクセスとタスクの認証・秘密値管理を検証する。外部実行者に一般職員の権限を与えず、採用方式の実測まで統合受け入れを完了にしない。

### Siteから専用ワーカーへ退避する場合

**案A:** D1とR2を正本に保ち、Cloud Tasks／Schedulerが専用のCloud Runワーカーを起動する。ワーカーはSitesの保護された業務APIだけを通じてジョブを取得・確保し、必要なファイルを読み、投稿結果と状態を返す。D1・R2へ直接接続しない。Site側APIはジョブ種別、対象ID、状態遷移と権限を制限し、Sitesのサービスアクセスまたは検証済みの専用認証で外部呼出しを検査する。サービスアクセスは職員本人のIDを与えない。画像・PDFの転送量、タイムアウト、重複配送時の排他、トークン更新の責任も小さな実証で確認する。

**案B:** 案Aの認証・ファイル転送・状態更新を安全に成立させられなければ、DBとファイル保存を含めて既存GCP側を正本に残し、Sitesは画面配信だけに用いる。この場合はD1・R2移行を採用しない。どちらの案でも同じ記録を両DBで別々に更新しない。選択条件と検証結果は[Issue #6](https://github.com/nto300002/kiiya-cleaning-checker-site/issues/6)に記録する。

## 移行しないもの

元リポジトリのGCP実リソース、既存PostgreSQL、Cloud Storageオブジェクト、Chatworkトークンをこの公開リポジトリへ複写しない。元の稼働系を切り替える作業も、この設計案の作成には含めない。
