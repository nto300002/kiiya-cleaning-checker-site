# Sites構成と移行境界

## 候補構成

| 現行の設計 | Sites版の候補 | 検証条件 |
| --- | --- | --- |
| Firebase HostingのReact PWA | SitesのVinext/Worker画面 | スマートフォン表示、既存画面フロー、オフライン入力、カメラ・画像選択を実機確認 |
| Cloud Run API・非公開ワーカー | Sitesのサーバールート／Worker | 認証・認可、PDF生成、Chatwork HTTP通信、処理時間とメモリを検証 |
| Cloud SQL for PostgreSQL | SitesのD1 | 制約、版固定、競合更新、冪等性、複数書き込みの整合、復元方法を検証 |
| 非公開Cloud Storage | SitesのR2 | 画像・報告ファイルの非公開参照、一覧・削除、保存期限、容量を検証 |
| Secret Manager | Sitesのホスト済みシークレット | OAuth秘密値・トークンをサーバーのみから使用。ローテーションとアクセス制御を検証 |
| Cloud Tasks・Cloud Scheduler・Cloud Run Jobs | Sitesで利用可能な定期更新、または別の認証済み外部実行基盤 | 1分監視、5分照合、日次期限処理、再配信・重複防止、障害復帰を実測 |
| Google IDトークンと職員台帳 | Sitesで利用可能なサインインと明示的な職員登録 | 元IDとの対応、IT権限、退職者の遮断、全職員閲覧を確認 |

SitesのWorkerはCloudflare Workers上で動き、HTTPによる外部接続が前提で、raw TCPは使えない。したがって現行のPostgreSQLドライバーとGCPメタデータ認証を移植せず、D1/R2とSitesの認証・シークレットに合わせて作り直す。Site用のD1/R2はホスティング設定の論理バインディングとして宣言し、資格情報をソースへ置かない。

## 公開範囲と認可

GitHubリポジトリがpublicでも、作業データを載せるSiteは職員限定を前提とする。Siteの公開範囲と認証方法は別途確定する。Sitesのサインイン情報だけで職員資格を認めず、サーバー側の`AppUser`有効状態と権限を毎回確認する。公開アクセスを選ぶ場合も匿名APIには記録・画像・報告・設定を返さない。画像は公開URLを発行せず、認可付きのサーバールートから返す。

## Chatworkと非同期処理

ChatworkのOAuth認可コード、state/PKCE、ルーム名確認、本文・PDF・画像投稿はWorkerからのHTTP通信を候補とする。投稿後の状態は成果物ごとに保存する。外部投稿とD1更新は同一トランザクションにできないため、既投稿照合、`Unknown`、手動確定、冪等な処理を維持する。

Sitesの定期更新が、既存要件の1分監視と5分後の照合を保証できるかは未確認。保証できない場合は外部キュー／スケジューラを維持し、Site側に認証済みの実行入口を設ける。外部実行者に一般職員の権限を与えない。採用する方式を実測するまで、報告送信・マスタ通知の統合受け入れを完了にしない。

## 移行しないもの

元リポジトリのGCP実リソース、既存PostgreSQL、Cloud Storageオブジェクト、Chatworkトークンをこの公開リポジトリへ複写しない。元の稼働系を切り替える作業も、この設計案の作成には含めない。
