# 旧作業の所有者対応手順案

SitesのサインインIDはSiteごとに異なるため、検証SiteのIDを本番の所有者IDとして使わない。共通アカウントの利用回避は人の運用で管理するが、**旧作業を誰が編集できるか**は移行前に確認済みの対応表で固定する。

1. 移行担当者が既存DBからGoogleの不変ID、旧`AppUser` ID、所有作業数を抽出する。氏名だけで同一人物を決めない。対応表と作業内容は公開GitHubへ保存しない。
2. 職員本人が**本番Site**へ各自のChatGPTアカウントでサインインする。Siteが受け取る安定したユーザーIDを職員台帳へ仮登録し、本人との照合を担当者が対面など既存の職員確認手段で行う。
3. 移行担当者が旧Google IDと本番SiteのユーザーIDを1対1の候補として記録し、別の確認者が職員台帳・本人確認結果と照合して確定する。同一のSite IDが複数職員に割り当てられる候補、旧IDの重複、共通アカウントと判明した候補は確定しない。
4. 対応が確定した作業だけ、新しい作成者IDで編集権限を復元する。対応不能・退職・本人不明の所有者の記録は元の所有者識別子を監査用に保持し、Sites側では**閲覧のみ**にする。未送信作業は任意の他職員へ自動譲渡せず、運用上の個別判断を記録する。
5. 移行前後の作業件数、確定・未確定の所有者件数、編集許可・拒否の実試験を記録する。対応表はアクセスを制限した運用保管先に置き、保持期限・削除担当を決める。

この手順は設計案であり、担当者・照合資料・保管先・未確定作業の最終運用は実データ移行前に決める。[Issue #2](https://github.com/nto300002/kiiya-cleaning-checker-site/issues/2)と[Issue #8](https://github.com/nto300002/kiiya-cleaning-checker-site/issues/8)で受け入れる。
