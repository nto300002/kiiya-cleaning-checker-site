# Sites版の受け入れケース（設計段階）

案A（SiteがD1/R2とトークンの正本、Cloud RunがChatwork投稿・非同期実行）を採用方針とする。以下のケースは**全件未実施**。Issue #1では必要な最小内部契約だけを仮置きし、案Aで実装を続けられると判定した後、Issue #3でSites版OpenAPI・D1/R2スキーマ・配備コミットとの対応を固定する。APIを呼ぶケースは`operationId`、画面比較は画面IDと参照版、移行・復元は手順IDと証跡、外部配送は構成IDと実行ログへ対応付ける。対応表がないままIssue #9を合格にしない。元の[業務テストケース](baseline/test-cases.md)も引き続き適用する。

| ID | 条件・操作 | 合格条件 |
| --- | --- | --- |
| `SITE-AUTH-01` | 匿名・無効職員・有効職員・作成者で作業、画像、報告にアクセス | 匿名/無効職員は拒否、有効職員は閲覧可、編集は作成者のみ。IT設定はIT担当者のみ |
| `SITE-AUTH-02` | 本番Site IDと旧Google IDの対応を確認し、重複・不明の旧所有者を含めて移行 | 確定した本人だけ編集可。不明所有者は閲覧のみで自動譲渡されず、件数が一致 |
| `SITE-TOKEN-01` | IT担当者がChatwork OAuth接続。保存失敗も注入 | D1へ暗号化した初回トークンを保存してから接続済み。失敗時は接続済みにしない |
| `SITE-TOKEN-02` | 2処理が同時にトークンを更新 | 1処理だけがリースを取得し、古い結果は新しい行を上書きしない。平文を通常ログ・職員向け応答へ出さない |
| `SITE-TOKEN-03` | Chatwork更新成功後にD1保存失敗、再接続、暗号化鍵更新 | 不整合を成功とせず再接続を要求。再接続後に実送信でき、旧鍵廃止後も復号できる |
| `SITE-TOKEN-04` | 確保済み・未確保・期限切れの各ジョブから投稿用トークン取得を試し、Cloud Runのログ・永続保存も確認 | 有効な投稿ジョブだけアクセストークンを取得。更新はSite側のみ。更新トークンや平文アクセストークンがD1、通常ログ、タスク本文、永続保存に残らない |
| `SITE-CHATWORK-01` | Issue #10で固定したSite・コールバック・D1・環境ゲートを照合し、IT担当者が検証用OAuthクライアントで接続。認可拒否、state・PKCE不一致、期限切れ、初回保存失敗、非ITアクセスも試す | 環境ゲートとIT権限がなければ拒否。`GET /me`のアカウントIDをIT担当者が固定し、暗号化保存とID確認後だけ投稿可能。異なるIDで再接続すると再確認待ち |
| `SITE-CHATWORK-02` | APIで検証用ルームを取得・選択し、別ルームIDへの投稿と参加権限なしを試す。Chatworkの`rooms.messages:write`の対象と操作範囲も確認 | ルーム名と参加権限を確認してサーバー側に1件固定。選択外の宛先と編集・削除操作をアプリが提供しないことを確認し、広いスコープの残余リスクを記録 |
| `SITE-CHATWORK-03` | IT担当者が一意のテスト本文1件を選択済みルームへ投稿。応答喪失・401・403・429も確認 | 成功時は`message_id`と画面の投稿が一致。応答喪失時は識別子で「投稿あり／投稿なし／判定不能」を手動照合し、判定不能を自動再送しない。401・403・429を区別し、Site直接投稿をCloud Run経由の報告送信合格に流用しない |
| `SITE-D1-01` | 並行PATCHと報告版確定、同じ冪等キーの再実行 | 作業と報告版が食い違わず、版番号・送信状態が維持される。異なる本文は409 |
| `SITE-D1-02` | マスタの別職員確認と同日予約の競合 | 編集者が確認できず、予約競合は409。取下げ後も版と確認記録が残る |
| `SITE-D1-03` | 書込停止後にアプリ表をページ単位で退避し、別の空の検証Site/D1へ復元。途中失敗と再実行も試す | スキーマ版・件数・ハッシュ・報告版とR2参照が一致し、元Siteに変更がなく、手順と保管先の証跡が残る |
| `SITE-R2-01` | 画像・報告ファイルの上書き、除外、報告版参照、匿名取得 | ID再利用を拒否。報告版の参照を維持し、匿名と無権限者へ画像を返さない |
| `SITE-R2-02` | 24時間超の孤立報告ファイル、送信済み版、7日期限の未送信版を混在させ日次実行 | 孤立・期限対象だけ削除し、送信済み版を保持。件数、所要時間、失敗後の再実行を記録 |
| `SITE-JOB-01` | Cloud Tasksから認証付きでCloud Runへ個別投稿・5分後照合を配送。無認証・重複・応答喪失も試す | 無認証呼出しを拒否。同じ報告ID・成果物を二重送信せず、結果不明を自動再送しない |
| `SITE-JOB-02` | Cloud SchedulerからCloud Runへ毎分監視と日次期限処理を起動 | 実行時刻、遅延、停止後復帰、処理IDと結果を確認。タイムアウト内に完了 |
| `SITE-JOB-03` | Cloud RunからSite内部APIへジョブ確保、R2成果物取得、D1結果保存を試す。認証なし、権限外ジョブ、失効リース、転送中断も試す | サービス認証とジョブ権限を強制。正本はD1/R2のみ、部分失敗後も再開でき、二重更新・二重投稿を防ぐ |
| `SITE-UI-01` | 固定したKIIYAデモ参照版とモバイル実機を比較し、開始から報告確認まで操作。トイレ・シャワーのドラム、客室切替、未入力案内、時刻編集も試す | デモを参考にした配置と操作順が成立し、意図的な差異を記録。新版業務要件と矛盾するデモの旧表示は採用しない |

各ケースには`共有SHA／Sites配備版／Cloud Run配備版／日時／実行者／環境／対応するoperationId・画面ID・手順ID・構成ID／期待・実結果／合格・不合格・未実施／証跡／残課題`を記録する。`SITE-AUTH-02`は所有者移行手順、`SITE-D1-03`は退避・復元手順、`SITE-UI-01`は画面ID、`SITE-JOB-01/02`は配送構成と実行ログを主な対応先とし、呼び出すAPIがあればその`operationId`も併記する。実Chatwork投稿は専用検証ルームのみで行う。案Bは採用していないためGCPをデータ正本とするケースは判定対象に含めない。案を変更する場合は対応するケースを先に定義し、D1/R2ケースを合格として流用しない。
