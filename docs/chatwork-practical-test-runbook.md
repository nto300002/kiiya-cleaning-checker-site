# Chatwork連携・実務利用テスト手順

作成日: 2026-10-27

対象: KIIYA見落としチェッカーの本番用Chatwork送信設定、確認投稿、業務報告送信

判定先: [Issue #5](https://github.com/nto300002/kiiya-cleaning-checker-site/issues/5)・[Issue #9](https://github.com/nto300002/kiiya-cleaning-checker-site/issues/9)

## まず確認すること

この手順は**実務利用を許可するための試験**であり、手順書の作成自体は試験合格を意味しない。2026-10-27時点のSiteには、設定画面・チュートリアル・送信元とルームの確認操作まである。一方、画面の「確認文を送る」は準備中で、Cloud Run経由の業務報告送信も受け入れ前である。実行できない行は「未実施」と記録し、成功に読み替えない。以前の検証用ルームへの本文1件の到着は、本番ルームや報告一式の合格証跡に使わない。

業務ルームへの試験投稿は、ルームの管理者・受領担当者と実施時刻を調整してから行う。テストには架空の氏名・架空の作業内容を使い、本文に「テスト」と識別番号を入れる。送信結果が不明なときは同じ操作を繰り返さず、Chatworkの画面と設定担当職員に確認する。

### 役割

| 役割 | 担当すること |
| --- | --- |
| 設定担当職員（`manage_chatwork`保有者） | 投稿元アカウントの接続・本人確認、業務ルームの入力・名称確認、確認投稿の照合、停止・再開 |
| 職員A・職員B | それぞれ自分のSitesアカウントでサンプル作業と報告を作成し、到着内容を確認 |
| 受領担当者 | 業務報告ルームで投稿者・識別番号・報告内容と添付を確認 |
| 職員管理者（`it`保有者） | 設定担当職員へ`manage_chatwork`を付与・剥奪し、操作履歴を確認 |
| 開発・運用担当者 | 配備、ワーカーとキューの健全性、障害注入、ログ・DB・R2の照合、復旧確認 |

`manage_chatwork`と`it`は別権限とする。通常職員はChatworkへ個別に接続しない。Chatworkへの投稿元はアプリの送信設定1件に固定し、作業の作成者はSites側で記録する。

## 実施前の確認（開発・運用担当者と設定担当職員）

以下が揃わない間は、後続の該当試験を「未実施」とする。

- [ ] 共有する設計・OpenAPIのコミットSHA、Site配備版、Cloud Run配備版、実施日、実施者、試験環境を非公開の試験台帳に記録した。
- [ ] 本番用OAuthの設定、暗号化鍵、D1の本番設定行・移行、Cloud Tasks、Cloud Run、内部API、毎分監視と認証済みハートビートを確認した。秘密値は記録しない。
- [ ] 設定変更・監査・候補失効の原子的更新、送信元再確認時の送信先確認状態、D1設定行欠落時の503、トークン更新成功後のD1保存失敗時の再接続待ちについて修正・回帰試験を確認した。未修正なら本番OAuthと実務送信の試験を開始しない。
- [ ] 投稿元に使う既存Chatworkアカウント、業務報告ルーム、設定担当職員と代行者、受領担当者、障害時の連絡先を決めた。対象アカウントが業務ルームに参加し投稿できるかを本手順で確認する。
- [ ] 業務ルームでの試験投稿の許可、実施時刻、テスト文の識別番号、試験後の取扱いを受領担当者と共有した。
- [ ] 設定担当職員に`manage_chatwork`が付与され、一般職員と職員管理者には不要な権限を付与していない。

記録先は**非公開の試験台帳**とする。公開GitHubには本番room ID、`account_id`、職員の実名、OAuthコード・トークン、報告本文、画像、画面の未加工スクリーンショットを載せない。GitHubのIssueにはケースID、判定、伏せた証跡への参照、残課題だけを書く。

## A. 設定担当職員の画面操作

各行の結果を末尾の記録表に転記する。画面の文言が異なる場合は、実際の文言と配備版を記録して手順を更新する。

| 手順 | 画面で行う操作 | 期待する結果 | 対応ケース |
| --- | --- | --- | --- |
| A1 | Siteへサインインし、「今日の作業」の「設定・アーカイブ」を開く。黄色のChatwork未連携案内を確認する | 未設定なら案内が出る。清掃記録は使えるが、業務報告の送信はできない | `SITE-UI-02` |
| A2 | 「設定」の「Chatwork連携」を開き、「チュートリアル」を進める | 操作箇所が順番に強調され、入力内容の説明が読める。設定担当者だけが変更フォームを操作できる | `SITE-UI-02`, `SITE-CHATWORK-07` |
| A3 | 「Chatworkアカウントを接続」から、決めた投稿元アカウントで認可する | 戻った画面に表示名が出る。詳細の`account_id`を非公開台帳の予定IDと照合し、一致するまで送信元を確定しない | `SITE-TOKEN-01`, `SITE-CHATWORK-04` |
| A4 | 業務報告ルームのIDを入力し、ルーム名を表示する | 入力したIDと取得したルーム名を一緒に見て、受領担当者が示したルームと一致することを確認する。違えば保存しない | `SITE-CHATWORK-08` |
| A5 | 正しいルームなら「このルームで間違いない」を押す | 確定後も「送信先の確認待ち」であり、「業務報告を送信可能」にはならない | `SITE-CHATWORK-06`, `SITE-CHATWORK-08` |
| A6 | 確認文送信が実装・有効化されたら、固定の個人情報を含まない確認文を**1回だけ**送る | 画面に確認用識別番号と「送信中／到着待ち／結果不明」などの状態が出る。投稿前に設定を変更した旧ジョブは別ルームへ送られない | `SITE-CHATWORK-09`, `SITE-CHATWORK-11/12` |
| A7 | 受領担当者とChatworkを開き、ルーム名・投稿者名・識別番号を照合。「届いた／見つからない／判断できない」を記録する | 投稿IDと画面の投稿が一致したときだけ`DestinationVerified`。不明なら再投稿せず担当者へ連絡 | `SITE-CHATWORK-06/09` |
| A8 | 「送信先を確認済み」と「業務報告を送信可能」の表示を別々に確認する | `DeliveryEnabled`は承認済みワーカー・キュー・内部API・直近3分の正常ハートビートと運用有効化まで揃ったときだけ真 | `SITE-JOB-06/10` |

**現在の停止点:** A6のボタンは「確認文を送る（準備中）」のため、A6以降は現時点で未実施とする。A5まで操作できても本番宛先の投稿権限を証明したことにはならない。

## B. 職員2名による業務報告の到着確認

この節はA7の合格と送信経路の受け入れ後に実行する。実際の宿泊者情報や画像は使わず、専用のサンプル作業を用意する。

| 手順 | 行う操作 | 期待する結果 | 対応ケース |
| --- | --- | --- | --- |
| B1 | 職員Aが自分のSitesアカウントでサンプル作業を作り、必要なチェック・最終確認・備考・試験画像を入力する | 他人の作業を編集せず、プレビューに入力内容と作成者が出る | `SITE-AUTH-01` |
| B2 | 職員Aが報告版を確定し、表示された送信元名とルーム名を確認して1回送信登録する | 報告ID・版・送信ジョブIDが分かる。ボタン連打や同じ要求の再操作でジョブが増えない | `SITE-D1-04`, `SITE-JOB-04` |
| B3 | 受領担当者がChatworkで本文、`.md`添付、画像入りPDF、画像ファイルを照合する | 同じ報告ID・版の成果物が指定ルームへ揃い、ファイル名・ハッシュ・投稿ID／ファイルIDと一致。アプリは全必須成果物の到着後だけ`Sent`、作業は`Completed` | `SITE-JOB-01/03` |
| B4 | 職員Bが**別のSitesアカウント**で別のサンプル作業・報告を作り、同じ手順で送る | 職員BにChatwork認証を求めない。Chatwork上の投稿元`account_id`はAと同じで、報告本文・履歴の作成者はA/BそれぞれのSites職員ID | `SITE-CHATWORK-04` |
| B5 | 職員A/Bと受領担当者が内容を業務上読めるか確認する | 作業別の対象・担当・時刻、備考、不備、添付の対応が分かる。不足・誤送信は不合格として報告IDとともに記録 | [業務テストケース](baseline/test-cases.md) |

報告版だけ作成できて送信登録が失敗した場合は、**同じ報告ID**から登録を再試行する。投稿開始後の結果不明はB2を繰り返さない。実装された状態画面とChatworkを照合し、開発・運用担当者へ引き継ぐ。

## C. 開発・運用担当者が再現する失敗・復旧試験

業務ルームへの意図しない投稿を防ぐため、障害注入は分離した検証環境または受領担当者と調整した限定時間帯で行う。設定担当職員には画面に現れた状態と必要な対処が分かるかを確認してもらう。

| 試験 | 合格の観点 | 対応ケース |
| --- | --- | --- |
| 権限: 一般職員、`it`のみ、`manage_chatwork`のみ、剥奪後 | 設定API・職員管理APIが役割どおり403。付与・剥奪、未適用変更・未投稿確認ジョブの終了を監査できる | `SITE-AUTH-03`, `SITE-CHATWORK-13` |
| 初回・更新トークンの保存失敗、同時更新、認可失効 | 保存失敗を接続済みにしない。Chatwork更新成功後にD1保存が失敗したら`ReconnectRequired`。トークンを応答・ログに出さず、再接続で復旧 | `SITE-TOKEN-01/02/03/04`, `SITE-CHATWORK-05` |
| ルーム退出・投稿権限喪失、401・403・429 | 誤った`Sent`にならず、原因に応じて再接続・宛先再確認・待機を案内。別アカウント／別ルームへ自動切替しない | `SITE-CHATWORK-05` |
| キュー投入失敗、重複タスク、応答喪失 | 未投入は同じ検証IDで監視が再投入。外部POST開始後の不明は`Unknown`となり自動再送しない | `SITE-CHATWORK-12`, `SITE-JOB-01` |
| 送信中の宛先変更・部分送信 | 旧投稿IDと旧宛先を保持し、同じ版の成果物が新旧ルームへ分かれない。不明時は手動照合する | `SITE-JOB-04/05/07` |
| ワーカー停止・復旧、手動停止・再開 | 3分超のハートビート欠落で送信登録不可。5分リース失効は監視で`Unknown`、旧ワーカーの更新・自動再送を拒否 | `SITE-JOB-08/10`, `SITE-CHATWORK-13` |
| 7日期限・保存物の回収 | 未投稿・部分投稿・成否不明を契約どおり区別し、送信済み成果物は誤削除しない | `SITE-R2-02/03` |
| 実行時間 | 本文、画像入りPDF、複数画像、Markdown添付の各構成を3回以上、遅延条件も測る。初期値ではPOST4分以内、リース取得からD1保存まで4分30秒以内。30秒以上の余裕がないなら再設定・再試験 | `SITE-JOB-09` |

## 利用開始の判定

1. A7の業務ルーム実投稿・人の照合が合格して初めて**送信先確認済み**とする。
2. Bの成果物一式、共通投稿元と職員別履歴、Cの失敗・復旧、`SITE-JOB-09`の実測、ワーカー経路と権限の試験が合格して初めて**実務送信を受け入れ**る。
3. [Sites固有の受け入れケース](sites-test-cases.md)と[運用・受け入れ](operations-and-acceptance.md)の対象ケースを合格／不合格／未実施で集約し、Issue #9へ非公開証跡の参照と残課題を記録する。未実施・不合格を残したまま本番利用可とは判定しない。

設定・配送の詳細は[本番設定API契約](chatwork-production-settings-api.md)、[画面・配信契約](chatwork-screen-and-delivery.md)、[実務前の決定事項](chatwork-production-open-decisions-2026-10-27.md)に従う。
