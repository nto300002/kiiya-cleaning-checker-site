# Sites版の業務要件

## 引き継ぐ業務規則

[元の要件定義](baseline/requirements.md)、[現場フィードバック](baseline/field-feedback-2026-10-16.md)、[決定事項](baseline/remaining-requirements-decisions.md)の業務規則を維持する。Sitesへの移行で清掃の判定条件を変更しない。

参照資料と記述が食い違う場合は、このSites版要件と[構成設計](architecture.md)を優先し、参照資料内では後日の[現場フィードバック](baseline/field-feedback-2026-10-16.md)で確定した不備登録などの条件を、旧[要件定義](baseline/requirements.md)の構成指定や[暫定決定](baseline/remaining-requirements-decisions.md)より優先する。

- 1日の作業は担当職員1名を固定し、参加スタッフ1〜5名、作業日、開始時刻、対象客室、作業別の担当・時間・完了を記録する。日付が変われば当日画面は新規入力となり、前日の保存済み記録はアーカイブで閲覧する。
- 新版の作業は**10種類**。ユニット1はベッドメイキング、アメニティセット、部屋掃除、廊下、階段玄関。ユニット2はシャワールーム、ラウンジ、洗面台、トイレ掃除、**洗面周り廊下**。旧「洗面周り床」は新規作業に設けない。
- 対象客室ゼロ件を認め、その場合は客室向け3作業、客室チェック、職員最終確認を報告必須条件から外す。全室が連泊・アメニティのみならベッドメイキングと部屋掃除を外し、宿泊人数が1人以上の客室があればアメニティセットを必須とする。
- 対象客室を選択したまま宿泊人数を大人0人・子ども0人にできる。0人の客室は清掃種別にかかわらずアメニティセットの対象から外し、客室チェックのアメニティ・枕・設置場所を表示せず、報告必須条件からも外す。通常清掃・連泊清掃の清掃項目と職員最終確認は残す。連泊・アメニティのみの0人客室は対象室として記録し、個別チェック項目はないが職員最終確認を必須にする。全対象客室が0人ならアメニティセット作業は必須としない。人数変更により対象室や必要項目が増えた場合、旧回答・旧完了を新しい対象の完了判定に流用しない。未解消不備は非表示項目に紐づいても報告を止める。
- トイレは対象数0〜2、シャワーは0〜3をドラムピッカーで選択する。実施数の入力はシャワーだけ。客室の回答は清掃種別別に保持し、旧種別の回答を新種別の完了判定に流用しない。
- 問題は現地で備考か個別の客室不備に分類する。備考だけでは報告を止めない。未解消不備は報告を止め、解消後は対象チェックと最終確認をやり直す。
- ログイン済みの有効な職員は全員の作業・画像・報告を閲覧できる。作業編集・画像変更・報告確定は作成者だけ。送信結果不明の手動確定は作成者またはIT担当者に限る。
- 報告版は確定時の内容と画像参照を固定する。PDFには画像を埋め込み、画像ファイルもChatworkへ送る。Markdownは本文投稿と`.md`添付を設定で切り替える。必要成果物がすべて確認された時だけ`Sent`とし、結果不明を自動再送しない。
- Chatworkの投稿元は環境ごとのアプリ送信設定1件に紐づけた既存メンバーのアカウント1件とする。専用の`manage_chatwork`権限を付与された設定担当職員が画面からOAuth接続し、`GET /me`のアカウントIDと表示名を確認・固定する。この権限だけでは職員管理APIを操作できない。設定担当職員が業務報告用room IDを画面へ入力し、APIで取得したルーム名を確認してDBの本番送信設定1件へ保存する。本番room IDを環境変数・ソースコードへ設定する作業やプログラミング知識は不要とする。テスト投稿でそのルームへの投稿権限を確かめる。現場職員ごとのChatwork認証は不要で、作業者・報告者はSites側の職員IDとして作業履歴と報告本文に残す。
- 既存の本番Site内で行う期限付きの検証用ルーム投稿は接続試験に限る。本番の送信先確認済みには、別途、確定した業務報告ルームで投稿権限を確認する。職員の報告送信はCloud Run・キュー・内部API・成果物保存経路の受け入れ後だけ有効にする。報告確定・送信登録は作成者だけが行い、確定済み報告IDから送信登録を再試行できる。同じ報告IDでジョブを二重作成しない。
- 送信ジョブに報告確認時の本番設定版・送信元`account_id`・宛先room IDを固定する。各成果物の投稿直前に設定を照合し、変更されていれば残りを保留して新しい宛先へ自動で振り替えない。既投稿IDと元の宛先は保持する。元の宛先で続けない部分送信はIT担当者が全投稿結果を照合して`Failed`へ確定し、作成者は新しい報告版を作る。成否不明なら`Unknown`を維持する。再開・新規版の扱いと画面権限は[Chatwork画面・配信契約](chatwork-screen-and-delivery.md)に従う。
- 無人の継続送信には`offline_access`とトークン更新を使う。投稿元の認可失効、アカウントIDの不一致、ルームからの退出・投稿権限喪失時は送信を停止し、`manage_chatwork`保有者に再接続または宛先の再確認を求める。送信できなかった報告を成功扱いしない。
- 初回報告ボタン押下から7日後、未送信確定の内容を削除する。未押下の下書きと送信済み版は無期限。`Sending`・`Unknown`は結果確定まで保持する。設定変更による保留は、既投稿0件なら7日後に期限切れとして内容を消去し、既投稿あり・成否不明なら結果確定まで保持して7日経過時に要対応を通知する。部分送信を`Failed`に確定したら未送信の7日期限へ戻す。報告番号、既投稿ID、保留・結果不明・期限切れの事実は所定の履歴として残す。
- マスタ変更は別職員1名から承認を得たという自己申告と氏名記録で申請する。通知成功だけでは適用しない。編集に関わらない別職員が完成版を確認し、その翌日0時（日本時間）から新規作業に適用する。旧作業・送信済み報告の参照版を変えない。

## Sitesへの置き換えで変わる範囲

画面の配信、サーバー、DB、ファイル保存、本人確認、秘密情報管理、定期・遅延処理の**実現方法**だけを再設計する。UIの外観と操作は[KIIYAデモの参照方針](ui-reference.md)に従う。業務上の画面条件は[本番画面構成](baseline/production-screen-flow.md)と[デモv14のUI設計](baseline/ui-design-v14-2026-10-16.md)を基準とし、デモ内の旧仕様をそのまま引き継がない。オフライン入力と競合時の再確認も維持する。

Sites版MVPでは、職員が**各自のChatGPTアカウントを使い、共通アカウントの利用を避けることを人の運用で徹底する**方針とする。共通利用をアプリが検知・禁止する機能は現時点では要件に加えない。アプリはサインインされたアカウントIDで作成者・閲覧者・IT担当者の権限を判定する。共通アカウントを使った場合、アプリだけでは実際の操作職員を区別できないため、作成者限定編集と監査記録の意味が弱まる。職員へのアカウント配布・利用停止の運用を決め、既存Google IDとの対応付けが必要な実データ移行時には別途確認する。

旧作業を移すときは[所有者対応手順](owner-mapping.md)に従い、Google IDと**本番Site**のIDを職員本人と照合する。対応不能の記録は別人へ自動譲渡しない。
