# Chatwork OAuthトークンの保存・利用境界（案A）

## 保存先と境界

Sitesのホスト済みシークレットには、配置時に管理するOAuthクライアント秘密値と**トークン暗号化鍵**を置く。OAuthコールバックや更新処理で変わるアクセストークン・リフレッシュトークンは、Site側Workerだけが暗号化してD1の接続行に保存・更新する。暗号文、nonce、鍵バージョン、期限、更新番号、接続状態だけを永続化する。平文トークンはブラウザー、公開リポジトリ、通常ログ、職員向けAPI応答へ出さない。Sites上の暗号化鍵・D1連携は実環境で検証する。

## 状態遷移

1. IT担当者のOAuth開始でstateとPKCEを短期保存する。コールバックでstateを消費し、認可コードをトークンへ交換する。**暗号化した初回トークンのD1保存が成功してから**接続済みとする。保存に失敗したら接続成功を返さず、再接続を促す。
2. 更新が必要な処理は接続行の更新番号と短期リースを条件に1件だけ取得する。取得者がChatworkへ更新要求を送り、返されたアクセストークン・必要なら新リフレッシュトークン・期限を**同じ条件付きD1更新**で差し替える。プロバイダーが新リフレッシュトークンを返さない場合は旧値を保持する。競合した処理は保存済みの新しい行を読み直す。
3. トークン更新はChatworkとD1にまたがるため完全に原子的にはできない。Chatwork側で更新に成功した直後にD1保存へ失敗すると、旧リフレッシュトークンが無効な場合がある。その際は成功を偽装せず`ReconnectRequired`としてIT担当者に再接続を求める。更新試行・失敗時刻と接続状態は記録し、トークンそのものは記録しない。
4. 再接続では新しいOAuth結果を同じ環境の接続行へ更新番号付きで置き、旧接続を無効化する。鍵の更新時は新鍵を先に配置し、既存行を再暗号化・検証した後で旧鍵を廃止する。鍵を失った場合の復旧は再接続とする。

## 実証すること

- 初回接続、同時更新2件、更新応答喪失、D1保存失敗、リフレッシュトークンのローテーション有無、再接続を専用の検証用Chatworkアカウントで確認する。
- 古い更新処理が新しいトークンを上書きしないこと、D1やログに平文が残らないこと、検証・本番の鍵と接続行が混ざらないことを確認する。
- Cloud Runワーカーはリフレッシュトークン、OAuthクライアント秘密値、暗号化鍵を取得・保存・更新しない。ワーカーが確保済みのジョブについて、Site側Workerは認証済み内部APIで投稿用アクセストークンと有効期限を返す。期限切れ時の更新はSite側だけで行い、ワーカーは必要なときに再取得する。アクセストークンをCloud Runの永続ストレージ、ログ、タスク本文、結果APIへ残さない。
- 内部APIはサービス認証に加え、ジョブID・有効なリース・許可された操作を検査する。応答をキャッシュせず、失効済みリースには発行しない。Chatworkの401時はSite側で更新したトークンを取得し直す。ただし投稿の成否が不明なら無条件に再送せず`Unknown`にする。ワーカーへの平文アクセストークン転送と失効・監査は検証環境で実証する。
