## 目的
案AでSite側WorkerがChatwork OAuthとトークン更新を担当し、Cloud Run専用ワーカーが投稿・結果照合を担当する経路を検証・実装する。

## 作業
- Issue #10のOAuth接続・検証用ルーム照合・本文1件の試験結果を前提に、報告成果物とCloud Run専用ワーカーの投稿経路へ進む。Siteからの試験用直接投稿を本番報告送信の完了として扱わない。
- 本番の送信設定は業務報告用room ID・ルーム名と、そのルームへのテスト投稿ID・画面照合を設定担当職員が確認してから`DestinationVerified`にする。Issue #10の検証用ルームでの成功を本番ルームの投稿権限として扱わない。職員の送信ボタンはCloud Run・キュー・内部API・成果物/結果保存経路の受け入れ後に`DeliveryEnabled`とする。
- 本番room IDは専用の`manage_chatwork`権限を持つ設定担当職員がアプリ画面で入力し、Chatwork APIのルーム名を見て確定する。職員管理の`it`ロールだけでは本番設定を操作できず、`manage_chatwork`だけでは職員管理APIを操作できない。DBの本番送信設定に保存し、変更者・日時・設定版を残す。開発者への伝達や環境変数の編集を運用手順に含めない。検証用固定room IDと本番room IDは分離する。
- 本番room確定後の`DestinationVerificationRequired`では、確認済み送信元・承認済みワーカー経路・直近の正常ハートビートを条件に`manage_chatwork`保有者の確認専用投稿を許し、通常報告送信は`DeliveryEnabled`まで拒否する。確認ジョブのDB保存後にキュー投入が失敗したら`DispatchPending`と投入意図を保持し、毎分監視が同一タスク名で再投入する。外部POST開始後の`Unknown`は再投稿しない。
- 手動停止中は通常報告・確認投稿とも新規POSTを禁止し、未投稿の確認ジョブを`Cancelled(Paused)`にする。送信先未確認でも正常なワーカー経路と`manage_chatwork`権限で停止解除でき、新しい確認投稿を起動できる。通常報告は人の照合で`DestinationVerified`になるまで禁止する。権限剥奪時は受付済み未適用`ChangePending`を`Failed(PermissionRevoked)`、未投稿確認ジョブを`Cancelled(PermissionRevoked)`にし、外部POST開始済みの1件だけ結果または`Unknown`を保持する。剥奪された担当者が起動した`Sent`は確認確定に使わず、新しい権限保有者が確認投稿から改めて操作する。
- `docs/chatwork-production-settings-api.md`の本番設定APIを実装し、送信元確認、room ID候補のプレビュー・期限付き確定、実投稿と人による照合、送信停止・再開を`chatwork_smoke`から分離する。OAuth認可とroom ID入力は別操作とする。
- 設定担当職員が接続・確認した既存Chatworkアカウント1件をアプリの本番送信設定1件に固定し、全職員の報告をその名義で送る。職員ごとのChatwork認証やトークンを設けず、作業・報告の操作者はSites職員IDを本文と履歴に残す。
- OAuth state/PKCE、コールバック、トークン更新、ルーム名確認、1ルーム設定を実証する。
- 無人送信に必要な`offline_access`を取得し、認可失効時は再接続、ルームからの退出・投稿権限喪失時は宛先再確認を設定担当職員に求める。いずれも送信を止め、別アカウントや別ルームへ自動で切り替えない。
- `docs/chatwork-token-storage.md`に従い、初回トークンを暗号化してD1へ保存してから接続済みにする。更新時は短期リースと更新番号で競合を防ぎ、アクセストークンと新リフレッシュトークンを同じ条件付き更新で差し替える。Sitesのホスト済みシークレットはOAuthクライアント秘密値と暗号化鍵に使い、Workerから更新されるトークンの保存先にはしない。
- トークン更新がChatwork側だけ成功してD1保存に失敗した場合の`ReconnectRequired`、再接続、鍵更新を実証する。
- 確保済み投稿ジョブだけがSite内部APIから投稿用アクセストークンを取得できるようにする。更新トークンはCloud Runへ渡さず、更新はSite側だけで行う。Cloud Runがトークンを永続保存・ログ出力しないことを確認する。
- PDF・Markdown本文／添付・画像ファイルの生成をSite側、送信をCloud Run側の実行時間・メモリ・サイズ上限で検証する。
- 成果物別投稿ID、`Sent`／`Failed`／`Unknown`、手動確定、重複回避を実装する。
- 報告確定と送信登録を分け、作成者だけに許す。報告版作成後に登録が失敗しても同じ報告IDで再試行でき、同一報告IDの重複登録は既存ジョブを返す。送信ジョブに確定時の設定版・送信元`account_id`・room IDを固定し、**各成果物の投稿直前**に設定が変われば既投稿IDを残して残りを保留する。再開時も別のルームへ無断で振り替えない。
- `ConfigurationChangedHold`の期限処理を既投稿0件と既投稿あり・成否不明で分ける。0件は初回押下から7日後に`Expired`として内容を削除し、既投稿あり・不明は結果確定まで保持して7日経過時にIT担当者へ要対応を通知する。削除と手動再開は状態版で競合を検出する。
- 部分送信済みの旧ジョブを元の宛先で続けない場合、IT担当者が全成果物の結果を照合し、既投稿ID・元room ID・未投稿分・理由・確認者を残して`Failed`へ手動確定する。成否不明が残る間は`Unknown`を維持する。作成者は旧ジョブの確定後に新しい報告版を作る。
- 投稿中のワーカー停止は5分の成果物リースと毎分監視で検出する。期限切れをD1の状態版・リースIDで条件付き`Unknown`へ遷移させ、待機中の設定変更を進める。外部POSTは4分以下で打ち切り、旧リースの遅延結果更新と自動再送を拒否する。監視が停止した場合は復帰後の初回実行で期限切れを処理する。
- `SITE-JOB-09`に従い、リース取得から結果のD1確定保存までを代表サイズ・遅延条件で実測する。POST単体とR2取得・必要なトークン更新・応答処理・D1保存を含む全工程を分けて記録し、初期の4分POST上限・5分リースに収まる余裕を確かめる。

- [ ] 本番room IDを画面から登録・変更できるのは`manage_chatwork`保有者だけ。サーバーで権限を検査し、ルーム名確認と明示確定を経てDBへ保存する。設定担当者の職員管理API操作と一般職員の設定API操作は403。報告送信APIから任意のroom IDを指定できず、値はソース・環境変数・通常ログ・公開Issueに残らない。

- [ ] 職員2名以上の異なるSites IDで報告を作成しても送信元`account_id`は同一で、本文・履歴には各作成者のSites IDが残る。一般職員にはChatwork認証を求めない。

- [ ] トークンはブラウザーや公開ソースに出ず、接続・解除・更新が動く。
- [ ] 初回保存失敗では接続済みにならず、同時更新で古いトークンが新しいものを上書きしない。
- [ ] 更新結果不明・D1保存失敗・再接続を検証し、平文トークンがD1・通常ログ・職員向け応答に残らない。
- [ ] 確保済みジョブ以外は投稿用アクセストークンを取得できない。Cloud Runは更新トークンを保持せず、アクセストークンをタスク本文・通常ログ・永続保存に残さない。
- [ ] PDFへの画像埋込とChatworkへの画像添付を実ルームで確認する。
- [ ] 全必須成果物確認後だけ`Sent`。部分成功や応答喪失を自動再送しない。
- [ ] 送信登録失敗後の同じ報告IDからの再試行、同一要求の重複登録、他職員からの確定・登録拒否、設定変更と未投稿ジョブの競合を検証する。設定変更後は保留し、新宛先へ自動で振り替えない。

- [ ] 保留の既投稿0件は7日後に内容を削除して再開拒否、既投稿あり・成否不明は結果確定まで保持し7日経過時に要対応を通知する。期限処理と再開の競合、監査記録の保持を確認する。

- [ ] 成果物POST中のワーカー停止とリース失効を再現し、毎分監視または復帰後初回監視で`Unknown`へ遷移する。設定変更の待機は解除されるが残りは送らず、遅延した旧リース結果と自動再送を拒否する。
