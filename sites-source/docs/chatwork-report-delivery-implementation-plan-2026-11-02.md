# Chatwork業務報告配送：残りの実装・検証手順

作成日: 2026-11-02。対象は再構築Site、検証GCP、利用者が確認したテスト用Chatworkアカウント・ルーム。関連: GitHub Issue #5、#6、#9、#12。目的は実務利用前に、報告版から本文・Markdown・画像・画像入りPDFまでを、認証された配送経路で実証し、障害時も誤送信・二重送信しない状態にすること。

## 現状と判定の前提（2026-11-02〜03の作成当時の記録）

以下は作成当時の観測であり、現在の配備状況を示さない。後続の進捗記録とIssue #12を参照し、実環境の最新状態は都度確認する。

- 確認投稿は新URLのテストルームで実送信済み。報告配送の成功ではない。新たな実送信はテストデータを使う。
- ローカルには未コミットの配送基盤、0010移行案、成果物一覧の封印、職員版による失効、履歴の一部がある。ジョブ作成と一覧封印は別のbatchで、未封印・未投入の失効復旧が必要。実D1・公開Siteに未適用。ローカル版はレビュー・固定するまで配備版とみなさない。
- 報告確定はMarkdownのPrepared保存まで。送信登録API、成果物API・ワーカーの報告配送、PDF生成、報告タスク投入・結果確定は未完成。確認投稿の監視経路から通常報告を送れると仮定しない。現行の報告送信可能表示と承認は無効のまま。
- 過去の観測ではGoogle Cloud CLIのOAuthトークン取得がタイムアウト。HTTPS接続は確認できたが原因・中断した主体作成の成否は未確定。環境は実施前に再確認する。
- 現行OAuthスコープは `users.profile.me:read rooms.info:read rooms.messages:write offline_access`。Chatwork公式仕様ではファイル投稿に `rooms.files:write` が必要。これは参加ルームへのファイル投稿権限で、テストルームだけに限定する権限ではない。アプリ側で許可済み送信先へ固定し、権限の追加と再認可は実施時に利用者へ具体的に確認する。読み取りによるファイル照合を採用する場合、必要なreadスコープも仕様と最小権限を確認する。
- アプリの画像受け入れは最大8,000,000バイトだが、Chatworkのファイル投稿APIはファイル上限5 MB。PDF・Markdown・画像それぞれでサイズ・形式・生成後サイズを検査し、上限超過は送信開始前に利用者へ示して停止する。圧縮・変換・分割は品質と仕様を定めるまで勝手に行わない。厳密なバイト境界は実サービス仕様で確認し、安全側に設定する。
- OAuthとサイズの根拠: https://developer.chatwork.com/docs/oauth 、https://developer.chatwork.com/reference/post-rooms-room_id-files 。実環境の契約・権限・制限値は実測する。
- 本番Siteは現在テスト段階だが所有者限定を維持する。非公開情報・トークン・room ID・投稿ID・本文を公開Issueに記録しない。実行結果は日時、対象環境、SHA、Site版、revision、担当、結果、非公開証跡参照で記録する。

## 実施順・受け入れ条件

チェックは当該行の条件をすべて満たした場合だけ入れる。途中までなら未チェックのまま、合格・失敗・未実施と原因を記録する。1〜4の開発と5の環境診断は独立に進められる。6以降は前提を満たしてから行う。

### 1. 対象固定と認証・サイズの仕様

- [ ] **P01 固定**: 既存の未コミット差分を保全・レビューし、作業カード変更と配送変更を区別。Issue #5/#6/#9/#12、Site版、GCP、D1 binding、実行主体、OAuthクライアント、テスト送信先を照合し、コミットを固定。対象は非公開台帳に記録する。
- [ ] **P02 権限と再認可**: 現在のOAuthクライアント・認可済みscope・テストルームへの権限を確認。ファイル投稿scope、必要な読取scopeと既存接続への影響を特定し、利用者に具体的な権限追加を確認。承認後にクライアント設定・要求scopeを更新、再認可・暗号化保存・送信先再確認を行う。未承認・拒否・範囲不足はファイル配送を停止し、送信可能と表示しない。
- [ ] **P03 生成物とサイズ**: 本文、Markdown、PDF、画像の順序と各成果物の識別子・ファイル名・保存先・保持期限を固定。画像入りPDFのフォント・日本語・画質・空画像・複数画像と容量を定義。元画像8 MB以下でも生成物がChatwork上限を超える場合、外部POST前に具体的なエラーを返し、処理・再選択の操作を用意する。境界値、画像破損、拡張子・MIME不一致、空ファイル、最大枚数、生成失敗をテストする。

### 2. TDDで報告登録と成果物の永続化

- [ ] **P04 報告登録API**: 作成者・現場職員の認証、CSRF/origin、現行職員版、最新確定報告版、確認済み送信元・送信先・設定版、正常heartbeatをサーバーで検証。通常登録はP22の実務送信許可、試験登録はP18Aの限定許可を別々に検証。任意room・本文・R2 key・OAuthトークンを受け取らない。同一報告IDの再要求・応答喪失・同時要求は既存ジョブに収束。他職員・失効版・設定競合・無認証は拒否する。受付失敗後に同じ報告IDで安全に再実行できることをテスト。
- [ ] **P05 成果物の固定**: DBの保存済み報告snapshotから固定順序で成果物一覧を生成・封印し、報告ID・元宛先・職員版を保持。ジョブ作成と一覧封印が別batchである点は、未封印の回復条件を含めて検証。欠損画像・部分一覧・権限／設定変更・同時要求・SQL失敗を注入し、未封印で確保できず部分状態から勝手に送らないことを確認する。投稿IDがあるPending、理由NULLなどの矛盾状態は自動失効・再作成しない。
- [ ] **P06 PDF/R2**: 実画像を参照したPDFとMarkdownを固定報告版から生成し、安全なプライベート保存先へ保存。ジョブが固定した作業の成果物のみ取得でき、他作業・別版・期限切れ・サイズ超過は拒否。PDF内の画像・文字と元データの対応を自動／目視で検証。生成と保存の失敗・R2欠損はDB上の投稿準備確保前と証明できる場合のみ確定失敗とし、無断で代替物を送らない。

### 3. 非同期配送・失敗時の復旧

- [ ] **P07 内部API**: Google OIDC主体・audience・承認世代・ジョブ／成果物リース・設定版・送信元／宛先・職員権限・成果物順序をDB変更時と各POST直前に確認。短期アクセストークンは確保済み成果物にのみ発行し、refresh tokenや認証情報はTasks本文・ログ・永続ファイルへ出さない。データ取得とトークン取得の競合、旧主体・旧世代・権限取消・期限切れをテスト。
- [ ] **P08 Tasks/worker**: scheduler→monitor→Cloud Tasks→Cloud Run→Siteの既存の認証付き経路を拡張。初回タスク名、存在照会、404後の新名、409後の実在確認、重複タスクの単一確保、作成／保存失敗・再試行上限後の再投入をテスト。報告本文はmessages、添付はfilesへ送り、それぞれ対応する応答IDを記録する。file_idとmessage_idの違いを正規APIの応答で確認して別に扱い、片方を他方として仮定しない。
- [ ] **P09 成果物状態**: 各POSTに先立ち投稿準備の確保と状態・リースをDBで原子的に確定。成功応答と対応する識別子を保存し、必須成果物すべて確定後にのみジョブSent。401/403/429、異常応答、応答喪失、タイムアウト、結果保存失敗、プロセス停止、重複配送を注入。送信された可能性があればUnknownとして自動再送しない。POST 4分・リース5分等の設定は代表サイズで実測後に確定する。
- [ ] **P10 設定変更・権限変更**: 各成果物の直前に固定設定を再照合。本文だけ送信後の宛先変更では元宛先・投稿IDを保持し残りを保留、新旧ルームへの分散を禁止。旧職員版の未着手・未投入は条件付き失効。投稿開始済み、部分送信、矛盾データ、未封印でも投入やリースの痕跡がある場合は保留し、自動再作成しない。
- [ ] **P11 照合・復旧**: 職員向けに成果物別状態、既投稿、未投稿、確認者・理由を表示し、監査付きの手動照合APIを実装。Unknownを自動Failed/Sentにしない。未送信確定前には、旧ワーカーの停止・再開防止、実行中HTTP終了、取得済みChatwork資格情報の無効化を実証して隔離を記録する。リース切れだけでは旧POST開始を防げない。確認不能ならUnknown・送信停止を維持。旧報告の完了後のみ新報告IDで再登録し、同一IDの削除・流用で一意制約を迂回しない。
- [ ] **P12 検証器**: Issue #12 T02-3/T04-3〜6に従い、同一旧資格情報を独立検証器へ安全に一時メモリ受け渡し、旧ワーカー停止後に失効前後の対照と有効期限内の拒否を観測。ログ・永続領域へ秘密を残さず破棄。更新トークンは事前消費を避け、同一性や有効性を証明できなければ未判定。隔離後に新主体・資格情報を旧主体から分離して再認可し、heartbeat確認後に新試行する。

### 4. 画面・自動テスト

- [ ] **P13 画面**: 利用者は確認モーダルの「確定」1回で送信する。内部では報告の固定・配送登録・外部POSTを区別し、確定前の送信先・形式・添付・実際に送信する旨を表示、キャンセルでは配送登録・送信を行わない。結果画面は送信待ち・送信中・成果物別成功／失敗・Unknown・保留を区別し、更新失敗時も成功を表示しない。現場職員／通常職員の可視性、他人の編集禁止、再読み込み・複数端末・画面読み上げ・スマートフォンで確認する。
- [ ] **P14 TDD回帰**: 以上を失敗テスト→実装→成功の順に追加。SQLite模擬・HTTP・workerテスト、型検査・ビルド・0010の空DB／適用済みDB／途中失敗・rollback・再実行を検証。実D1 batch・トリガー・Tasksの動作にローカル結果を流用しない。公開Siteで実行中の作業表示変更は配送変更と分離し、対応版を明示する。

### 5. 環境障害の切り分け・配備

- [ ] **P15 Cloud認証回復**: 利用中のgcloudアカウントとプロジェクトを確認し、トークン取得を秘密を表示せず診断。期限・認証更新・ローカルプロキシ／ネットワーク・組織ポリシーを分け、タイムアウトの原因を記録。必要なら利用者本人にGoogleログイン／多要素認証を依頼し、秘密は受け取らない。前回中断したサービスアカウント作成が成功したかを先に照会し、結果不明のまま重複作成しない。権限不足なら必要な操作・ロール・対象をまとめる。
- [ ] **P16 実D1・移行**: 対象Site・binding・現在の移行履歴／スキーマ・0010適用有無を確認。新規再構築Siteと旧Siteを混同せず、他環境の履歴を書き換えない。トリガーがSitesの移行手順で適用可能か、D1 batchの原子性・並行競合を検証。ユーザーが旧データのバックアップ不要を承認したことは、新Siteの現データ消去や移行履歴の推測を許可するものではない。移行途中で結果不明なら配備を止め、実状態を確認してから追加修復を設計する。
- [ ] **P17 配備と認証**: 対象コード・画像digest・Site版・専用worker revision・サービスアカウント・キュー・OIDC audience・シークレット参照・IAMを照合。旧世代取消後、必要なら新主体を作成し、新版を監査付き承認する。公開未認証ディスパッチャーを作らず、既存の認証付きScheduler/Tasks/worker経路を使う。未認証、古い主体の偽版、誤audience、期限切れ、不正secretを拒否し、正規主体のheartbeatを確認。失敗時は承認前に戻すのではなく、安全に停止し配備状態と実行中ジョブを照合する。
- [ ] **P18 実環境の管理**: 検証ルーム・テストアカウントを作業前に再照合、外部連携への影響・失効操作・復旧担当を決める。実投稿は識別子付き・個人情報なし。Unknownなら再送・削除・新規試行しない。試験資材の削除、資格情報の復旧、旧主体遮断を後片付けとして記録する。

### 試験用の送信許可と実務送信の分離

方針として、P19より前に**期限付きの試験限定経路**を実装する。通常配送と別の送信実装や安全判定を作らず、同じジョブ・成果物・Tasks・ワーカー・結果保存を使用し、登録と各POST直前の許可条件だけを明示的に分岐する。試験経路の利用はP22の実務送信有効化を意味しない。

- [ ] **P18A 試験限定許可と無効化**: 認証・監査付き運用者操作で許可を作成し、有効期間・上限・承認世代・実Site版・worker主体／revision・digest・接続中アカウント・固定テストルーム・設定版・利用者が作成したテスト報告版ID・現場職員ID／職員版をサーバー側に束縛する。報告は個人情報のない専用データを使い、送信先と本文・添付はクライアントの任意値で指定させない。操作者は当該報告の作成者かつ有効な現場職員に限り、画面で「試験送信」と目的・ルーム名を明示して登録する。別の報告・職員・ルーム・アカウント・設定版・配備版、期限切れ、権限変更、承認取消、上限到達、試験モード指定のない通常要求は拒否する。
- 許可発行・変更・取消は運用者に限定し、実行回数の確保、報告ID固定、重複要求の同一ジョブ化、上限・期限の確認はDB条件と競合試験で保証。試験と実務はサーバー管理のジョブ種別／許可で区別し、試験許可から通常送信や他の送信先へ権限が波及しない。試験向けに許可された配備版と正常heartbeatを要求し、実務向けの `report_approved=0` と `DeliveryEnabled=false` は維持する。試験の許可は別管理し、実務承認を一時的に立てて代用しない。
- **取消・期限切れとの競合境界**: 各成果物の外部POSTに先立ち、試験許可の有効性・期限・対象・職員権限・配備承認とリースを条件付きSQLで確認し、「投稿準備確保」をDB上で原子的に記録する。取消は同じ許可の状態／世代に対するDB更新で直列化する。DB時刻・期限境界を規定し、確保より先に取消または期限切れが成立した場合は確保を拒否し、その旧試行のPOSTを開始しない。
- **確保後の扱い**: 投稿準備確保が先なら、取消・期限切れ時点でChatworkへのPOSTが観測されなくても旧ワーカーが後から開始できる可能性がある。取消は以後の新規確保を拒否し、当該成果物を結果不明として保留する。事前チェック、再確認やリース期限だけで未送信と判断しない。確定的な応答は承認主体・世代・リース等の安全条件を満たす場合だけ保存し、それ以外はUnknownを維持する。取消後も旧試行の結果を黙って破棄して未送信にしない。
- **隔離後の復旧**: 未送信確定や新しい試行は、P11・P12に従い旧ワーカー停止・再開防止、実行中リクエスト終了、取得済み資格情報の無効化等により旧POSTが今後開始されないことを確認し、投稿の有無を照合してから行う。いずれか不明ならUnknown・送信停止を維持。許可の期限切れ・取消やリース満了は隔離証明にならない。旧主体の承認取消と結果保存の競合には引き続き世代ガードを適用する。
- テスト終了時は新規受付・未確保の配送を無効化し、試験許可を取り消して監査する。送信中・Unknownは処理結果と旧試行の隔離を照合してから整理し、送信可能な状態で放置しない。テストジョブ・成果物の結果と監査証跡は保持する。期間満了・手動取消後は同じ報告の重複要求も新規配送を起こさない。
- 受け入れ試験: 許可された現場職員・報告・テストルームの実送信、通常職員／他職員／他報告／他ルーム・アカウントの拒否、期限・回数上限・設定版・主体／配備版変更、無認証、同時登録・応答喪失・二重配送、DB確保と取消／期限切れの競合、結果不明、後片付けと監査を自動・実環境で確認。特に、許可確認・DB確保後かつPOST前にワーカーを停止して取消／期限切れにし、再開で遅延POSTが起こり得ることを考慮し、隔離前の未送信確定・新試行を拒否する。P11・P12の停止・資格情報失効・通信終了を実証後に照合・復旧する。確保前に取消／期限切れとなった場合は確保・POSTが拒否されることも確認する。試験中と終了後に通常の実務登録が拒否され、`DeliveryEnabled=false` のままであることも確認する。

### 6. 実環境受け入れと実務開始

- [ ] **P19 試験配送**: P18Aの限定許可が有効な間、固定済みテスト報告を作成者が試験送信として明示的に登録。実務送信は無効のまま。本文、Markdown、画像入りPDF、複数画像を画面・実D1・Tasks・Cloud Run・Chatworkで成果物別に照合。各投稿数とAPIの対応IDが一致し、全成果物が揃ったときだけSentになる。サイトの再読込・二重操作・レスポンス喪失後も投稿が重複しない。
- [ ] **P20 障害と競合**: 401/403/429、実際のファイルサイズ超過、ネットワーク断、POST応答喪失、成功後DB保存失敗、ワーカー遅延／停止、リース切れ、停止中monitor、タスク上限、同時確保、職員降格、本文後の宛先変更を試す。部分結果を保持し、新旧ルーム分散・自動再送を防ぐ。ユーザー本人による照合操作・監査と復旧を実証。
- [ ] **P21 実機と権限**: スマートフォンで報告・添付・状態を操作し、通常職員・現場職員・別作成者で表示と直接API拒否を確認。別々の職員2名の報告が同じ承認済み送信元から送られ、本文・履歴に各作成者が保持されることを確認する。
- [ ] **P22 実務用切替・最終判定**: テスト先と異なる実務用Chatworkアカウント／ルームを設定担当が画面上で再設定し、専用確認投稿・本人照合を実施。監視、通知先、リカバリー担当、保管・復元、費用を確定。Issue #5/#9/#12の条件と明示的な運用判断が揃って初めてDeliveryEnabledを有効化。テストルーム成功やローカルテストだけでは実務可としない。

### 決定仕様：確認モーダルの「確定」で送信（2026-11-03）

利用者の最終決定として、試験と実務の両方で、確認モーダルの「確定」を押す操作を送信の開始とする。試験は固定テストルームと限定許可を使うが、職員の操作、報告の固定、成果物、配送・結果表示は実務と同じ経路を使う。P13の「分離」は内部の状態と責務の分離を意味し、職員が保存後に別の送信ボタンを押す意味ではない。既存の試験登録画面はこの一回操作に統合する。実装・実環境試験は未完了で、この決定だけで実務送信を有効化しない。

- [ ] **S01 確認内容**: 確認モーダルに実際の送信元・ルーム、作業日、編集後の本文、形式、画像・生成ファイルの種類と件数、確定するとChatworkへ送信を開始する旨を表示。試験時は「試験送信」と固定テストルームを明示。設定・許可・権限不足、期限切れ、添付・サイズ・生成不備、監視不健全を検出したら理由を表示して確定不可。キャンセル・閉じる・戻るは配送登録やPOSTをしない。
- [ ] **S02 試験許可と確定前の固定**: 既存P18Aが報告版IDとジョブを事前に固定する点と、一回操作を整合させる。確認画面を開く前に、編集確定済み本文・画像一覧・作業版・作成者をサーバーで不変の送信前スナップショットとして保存し、安定した報告IDを発行する。編集本文は作成者による事前スナップショット作成時に検証・保存し、送信登録要求には本文・添付・宛先の任意値を受け取らず保存済みスナップショットを使う。これは外部送信の意思確定や配送開始ではない。運用者がこのIDを含む固定条件で試験許可を発行し、職員は画面に許可待ち・失効を確認できる。確定前に本文・添付・作業・設定版が変わった場合、旧スナップショットと旧許可を送信に使わず、新しいIDと許可を必要とする。試験許可の発行自体は職員の確定前にPOSTを開始しない。通常経路には試験許可を流用しない。既存のreport/job/permitの外部キー・状態・監査を整合させるため、必要なスキーマ/APIの変更をTDDで実施し、スナップショットの再利用・期限・放棄時の扱いを実装時に固定する。
- [ ] **S03 一度だけの受付**: 確定要求はサーバー発行の安定したスナップショットIDと要求IDに結び付け、職員本人・職員版・作業版・内容・宛先・設定版・承認主体／世代・試験許可または実務許可をサーバーで再確認する。報告の送信意思、許可消費、ジョブと不変の成果物一覧の確定を原子的にするか、途中停止から安全に再開できる永続状態機械を用意する。外部POST前の状態が証明できない途中状態は保留し、自動で新ジョブを作らない。確定前のスナップショットの保存だけではワーカーが取得できないことをDB条件で保証する。
- [ ] **S04 二重操作と応答喪失**: 二重クリック、同時要求、複数端末、通信切断、保存成功後の応答喪失、再読み込みでは同じ要求IDとスナップショットIDを再利用し、同じ報告・同じ配送ジョブの状態に収束する。クライアントだけのボタン無効化に依存しない。確定の成否が不明なら照会し、新しい報告IDや要求IDを勝手に作らない。確定的に未受付と確認できた場合のみ同じ要求を再実行する。旧試行のUnknown・部分送信の隔離と照合にはP11/P12を適用する。
- [ ] **S05 状態と結果**: 受付済み、送信中、成果物別の送信済み・失敗・結果不明・保留を表示。全必須成果物の成功IDが保存されるまで全体を送信済みとしない。登録前に確定的に失敗した場合は理由と同一要求の安全な再開を表示し、投稿の可能性がある場合はUnknownとして自動再送しない。元のテストルーム・成果物・監査を保持する。
- [ ] **S06 TDD・実環境受け入れ**: キャンセル、許可待ち、確定前の編集、権限／設定変更、二重操作・複数端末・応答喪失、一覧封印・登録途中の失敗、POST応答喪失、部分送信・取消／期限切れの競合、隔離前の再送拒否、全成果物成功をAPI・DB・workerの自動テストで検証する。続けて個人情報のないテスト報告を固定テストルームへ「確定」1回で実送信し、本文・Markdown・画像入りPDF・画像、画面・実D1・Tasks・Cloud Run・Chatworkの投稿数とIDを照合する。試験許可なし・通常職員・対象外・実務送信無効では送信できないこと、試験終了後の許可取消も確認する。

### S02補足：スナップショットの作成・復旧と許可待ち（2026-11-03）

以下は決定仕様のS01〜S06を具体化する未実装の受け入れ条件である。送信先の制限、試験／実務の許可分離、POST後のUnknownと隔離条件は変更しない。

- [ ] **S02-1 作成要求と復旧**: クライアントは作成APIを呼ぶ前にUUIDの`snapshotRequestId`（実装上は空白なし）を生成し、作業ID・作業版・本人識別情報の非秘密メタデータと対応付けてsessionStorageに保存し、本文・添付は端末の永続領域に保存しない（詳細はB04/B05）。サーバーは本人認証、職員版・作業版を検証し、正規化方法を固定した本文・添付IDと作業ID・版・作成者のハッシュを計算する。作成要求IDの一意制約と入力の指紋をサーバーで保存し、同じID・同じ入力の再送は既存スナップショットIDと状態を返す。同じ要求IDで異なる入力は409として拒否する。異なる作成者の要求は拒否し、クライアントのハッシュは信用しない。
- [ ] **S02-2 別端末との収束**: 有効な送信前スナップショットは作業・作成者ごとに同時に1件に制限し、DBの一意制約と条件付き更新で作成を直列化する。別端末で同じ作業版・同じ内容を同時作成した場合は、それぞれの要求IDを既存の同一スナップショットに結び付けて返す。異なる内容・異なる作業版の競合では新たな有効候補を黙って作らず、現在の候補と競合を表示する。権限付き照会APIは本人に限り、作成要求IDまたは作業IDから有効候補・報告ID・指紋・許可状態・確定状態を取得できる。作成済みだが応答が失われた場合、再読み込み・端末保存値消失・別端末でも照会し同じ報告IDを回復できる。照会が失敗・結果不明なら新ID・許可を発行せず、再照会する。
- [ ] **S02-3 候補の更新**: 本文・添付・作業の版・職員権限・送信先設定など固定条件が変化した場合、サーバーは旧候補と許可を使用不可にし、理由を返す。新候補への切替は旧候補が確定・送信開始していないとDB上で確認し、旧許可の取消・履歴保持と新候補の作成を競合に安全な手順で行う。確定要求の有無が不明、処理中、部分送信、Unknownの場合は旧候補を置換せず、S04・P11/P12に従う。端末の編集途中は、既存候補を自動破棄せず、競合があれば利用者に再確認を求める。
- [ ] **S02-4 許可待ち画面**: 職員が報告プレビューで「送信内容を確認」を選ぶと、編集後の内容を固定し、試験中は固定済み内容・送信先・添付・「試験送信／運用者の許可待ち」を表示する。許可前は「確定」を無効とし、更新操作または自動更新で許可状況を照会する。運用者は固定された報告IDにだけ期限付き許可を発行し、職員がページを離れても同一候補の状態から再開できる。許可後は改めて送信元・ルーム・本文・添付・試験表示を確認モーダルに表示し、職員が「確定」を押したときだけ配送登録を開始する。実務では通常許可の確認に置き換え、同じ最終確認と確定操作を使う。
- [ ] **S02-5 待機中の変更・期限**: 許可待ち／許可後に本文・添付・作業版・職員版・送信先設定・配備承認の変更、許可取消・期限切れが起きた場合、画面は古い候補／許可が使えない理由と、再固定・再許可または管理者確認を案内する。許可待ち中に編集可能にする場合は新候補の切替条件を満たすまで確定を無効にする。表示が古いまま確定してもAPIがDB時刻と固定条件を原子的に再検証し、確定受付前の失効なら受付を拒否し、受付後・確保前の失効なら受付済みジョブを停止し未投稿の証拠を照合する。確保後の取消・期限切れは結果不明と隔離を含むB01〜B03を適用する。
- [ ] **S02-6 受け入れ**: 作成DB保存後・応答前の切断、同一要求の再送、端末データ消失、画面再読込、別端末の同一／異なる内容の同時作成、許可前の確定拒否、許可後の再表示・確認、待機中の編集・権限・設定変更、期限切れ・取消と確定競合を自動テストし、実D1と画面でも確認する。応答喪失や競合で有効候補・許可対象・配送が重複しないこと、旧許可では送れないこと、キャンセルで投稿されないことを照合する。

### S02補足：受付・確保の境界と共有端末（2026-11-03）

この補足はS02-1とS02-5の曖昧な表現を置き換える未実装の仕様である。受付の成立、各成果物の投稿準備確保、ChatworkへのPOST開始を別の事象として扱う。許可取消・期限切れはDB時刻と条件付き更新で各事象と競合を解決する。

- [ ] **B01 確定受付前の失効**: 許可取消・期限切れ・固定条件の失効が確定受付より先なら、確定要求を拒否し、送信意思・配送ジョブの受付も外部POSTも行わない。画面は「許可が無効です。内容を再確認してください」等と表示し、再固定・再許可または管理者確認を案内する。単なるスナップショット保存や許可発行は確定受付ではない。
- [ ] **B02 受付後・確保前の失効**: 有効期間内に確定受付済みでも、対象の投稿準備確保より先に許可取消・期限切れとなれば、その成果物を確保せず新規POSTしない。受付済みジョブを取り消さず、送信停止として履歴・理由を保持し、画面に「受付済み・送信停止（許可失効）」を表示する。ジョブ・全成果物に確保、POST開始、投稿IDなどの痕跡がないことをDB上の条件付き更新と監査で証明できる場合のみ、全体を確定的な未投稿として扱える。1つでも送信済み・確保済み・矛盾・証拠不足なら全体を未投稿としない。既送信成果物と元ルームを保持し、未確保分のみ停止し、確保済みの結果はB03とP11/P12に従う。停止と確保の競合は同一DB状態を条件とする更新で直列化し、負けた側は更新しない。再許可・新報告版作成は既存一意制約、送信済み・Unknownの扱い、監査を維持して設計・テストする。
- [ ] **B03 確保後の失効**: 成果物の投稿準備確保後は、ChatworkへのPOSTがまだ観測されなくても旧ワーカーが後からPOSTできる。新たな確保は停止し、確定的な結果を安全に保存できない当該成果物をUnknownとして表示・保持する。既に成功確定した成果物はそのIDと状態を維持する。未送信確定や新試行は旧主体の停止・再開不能、処理中要求終了、取得済み資格情報の無効化、ルームの照合をP11/P12どおり確認するまで拒否。リース期限だけでは解除しない。
- [ ] **B04 端末保存を最小化**: 応答喪失の復旧に必要な作成要求ID・作業ID・作業版・認証主体に対応する非秘密の識別子・作成時刻だけを、当該ブラウザーのsessionStorageに保存する。報告本文、添付内容、送信先、トークン、本文から推測可能なハッシュはlocalStorage・sessionStorage・ログに保存しない。編集途中の本文は画面のメモリ上だけとし、明示的に候補を固定すると本人限定の認証付きサーバー保存に移す。既存の作業入力のローカル保存機能は別途範囲を確認し、今回の報告編集本文をそこへ混ぜない。ブラウザーやタブを閉じると未固定の編集本文は失われることを明示する。
- [ ] **B05 復旧と消去**: 画面再読込時、端末IDを持つ場合は本人認証した照会APIで要求と候補を照合し、別アカウントなら端末メタデータを利用せず削除して内容を表示しない。端末データが消えた場合も本人限定の作業IDから候補を照会する。保存済み候補があればサーバー側の本文を本人に復元する。要求がまだ処理中・状態不明なら新規候補を作らず再照会する。サーバーが未作成と返しただけでは遅延中の旧要求が後から到着し得るため、再入力から新要求を作る前に、旧要求IDを原子的に取消・封鎖し、遅延到着も拒否されることを確認する。旧IDが確定済み／作成済みならキャンセル操作は失敗し既存状態を照会する。旧要求のIDすら失われ、到着中か特定・封鎖できない場合は新規候補を作らず、サーバー側で作業・本人単位の競合防止と遅延要求の期限・確定的なフェンシングを完了するまで保留する。本文がサーバーに保存されていなければ再入力を求める。確定受付後の端末メタデータはサーバー状態の回復を確認後に削除し、候補作成前のキャンセルは削除、作成中・不明時は安全に照会／封鎖後に削除する。ログアウト・アカウント切替時にもメタデータを削除し、共有端末で別利用者に表示しない。sessionStorageが利用できない場合も本人限定のサーバー照会と同じフェンシングで復旧し、安全にできなければ保留する。サーバー側候補と監査の保持期限・廃棄は実装時に明文化し、送信記録・Unknownは勝手に削除しない。
- [ ] **B06 境界・共有端末テスト**: 受付前失効、受付後・確保前の取消／期限切れ、確保直後の失効、確保と失効の同時競合、本文送信済み後の添付未確保失効を自動・実D1で検証し、受付履歴・各成果物・表示・投稿有無を照合。B02の未投稿証明を矛盾や部分送信で拒否し、B03の隔離前再試行を拒否する。共有端末で保存領域に本文・添付・トークンが残らないこと、キャンセル・確定・ログアウト・別ユーザー・再読込・タブ終了を検証する。候補保存直後の応答喪失、保存前の接続断、遅延した旧要求と封鎖・新要求の競合、要求ID消失、sessionStorage不可でも二重候補・二重投稿が起きないことを検証する。
