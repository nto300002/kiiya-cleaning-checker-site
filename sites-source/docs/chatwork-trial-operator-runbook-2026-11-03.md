## 配備前の確認

1. Siteとworkerの差分をレビューし、`0010`〜`0013`の適用履歴を実D1で確認する。Sitesは配備時に未適用の移行を実行するため、履歴や既存スキーマに不明点があれば適用を止める。空DBと既存の検証用DBで移行・ロールバック手順を検証する。
2. Chatwork OAuthクライアントに `rooms.files:write` を追加し、テストアカウントで再認可する。参加するルームへのファイル投稿を許可する権限である。発行済みトークンのスコープが明示されない場合は試験を開始できない。既存のアクセストークンに権限が自動追加されたとみなさない。
3. 新しいCloud Run revisionには専用の新しいサービスアカウント主体を使う。実際のrevisionとコンテナdigest、Site版、OIDC audience、タスク起動権限、共有秘密値、Scheduler、Tasksとサービス認証を照合する。旧主体を使い回さない。旧試行が実行中または結果不明なら隔離・照合を先に実施する。
4. Site側で `DELIVERY_TEST_ACCOUNT_ID` と `DELIVERY_TEST_ROOM_ID` を検証済みのテスト先に固定し、`DELIVERY_TRIAL_WORKER_SUBJECT` を新しい実行主体のGoogle数値IDにする。値は非公開で管理する。設定がない場合や主体が異なる場合、試験ジョブは旧ワーカーへ渡らない。
5. SiteとCloud Runを配備後、運用者認証APIで実配備digest・revision・主体・Site版を照合して承認し、正しい世代のheartbeatを確認する。無認証・旧主体・誤audience・不正秘密値での拒否を確認する。必要なChatwork再認可が完了するまで投稿しない。

## 個人情報を含まない試験報告の送信

1. 現場職員本人がテスト用作業を作成し、JPEGまたはPNG画像を選び、Markdown報告版を確定する。添付は1件5,000,000バイト以下、合計20,000,000バイト以下。生成PDFも5,000,000バイト以下。WebPとフォントにない文字は送信前に拒否される。
2. 運用者は報告版IDを非公開で照合し、`/api/chatwork/production/internal/control` に `issue-test-permit` を送る。本文には `action`、UUIDの `requestId`、UUIDの `reportId`、DB時刻から1時間以内のミリ秒Unix時刻 `expiresAt`、`reason`、`expectedGeneration` だけを指定する。運用者専用Bearer秘密値を使い、ルーム・アカウント・worker主体はSiteの固定設定と承認監査から導出する。秘密値はコマンド履歴、ログ、Issue、Tasks本文に保存しない。応答喪失時は同じ `requestId` と入力値で再送する。
3. 本人が確定済み報告の履歴を開き、表示された試験先を確認して「この報告を試験送信」を押す。登録と、報告スナップショットからの本文・Markdown・PDF・画像の生成／固定が順に行われる。未完成・容量超過・形式不一致・フォント取得失敗・無権限では投稿しない。失敗した場合は表示内容に従い、必要なら運用者が許可を取り消してから新しい報告版を作る。
4. 登録後は画面・D1・Tasks・Cloud Run・Chatworkを非公開で照合する。本文、Markdown、PDF、画像それぞれが一度だけ届き、メッセージIDとファイルIDの種類が一致することを確認する。ローカル模擬試験と実投稿を区別して記録する。

## 取消・期限切れ・結果不明

- 許可確保前の取消・期限切れでは新たなPOSTを開始しない。すでに成果物を確保した後は、POSTが見えていなくても結果不明として扱う。リース期限だけで旧ワーカーが投稿できないと判断しない。
- 運用者は旧主体の承認を取り消し、旧ワーカーの停止・再開不能・実行中リクエスト終了と、取得済みアクセストークン・更新トークンの無効化を別途実証する。Issue #12の失効前後対照、時刻、同一トークンの一時メモリ保持、秘密をログや永続領域に残さない条件に従う。証明できない場合はUnknownを維持する。
- `confirm-report-isolation` は運用者専用認証、`jobId`、現在の失効済み世代 `expectedGeneration`、`reason`、非公開証跡の識別子 `evidence` と、`workerStopped`・`tokenInvalidated`・`requestsEnded` の各 `true` を要求する。これは運用者の確認を監査するもので、停止や失効そのものを自動証明しない。
- 現場職員は元のテストルームを独立に確認し、結果不明の成果物を画面で照合する。送信済みの場合は種類に合うメッセージIDまたはファイルIDを記録する。未送信を確認した場合はその事実を記録する。隔離がない場合は照合操作を受け付けない。
- 一部だけ送信済みの場合、送信済みの成果物を自動で再送しない。残りの成果物は隔離後、画面から取得して手動で同じルームに送信し、そのIDを「送信済みを確認」で記録する。元の本文は確定済みMarkdownから確認できる。すべての成果物が送信済みと確認されて初めてSentとなる。すべて未送信なら失敗として確定し、新報告版・新許可を作る。確認できない・矛盾がある場合はUnknownを維持する。
- 試験終了時は許可を取り消し、実行中処理が残っていないことを確認し、証跡を非公開保存する。テスト接続・新ワーカーを再認可するときは旧主体が新資格情報にアクセスできないことを確認する。R2成果物および失敗途中に残ったオブジェクトの保持期間・削除方法は実務前に決定する。
