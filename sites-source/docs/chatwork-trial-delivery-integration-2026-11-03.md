# 試験限定の報告配送：接続手順・受け入れ条件

作成: 2026-11-03。対象: 再構築Site、検証GCP、利用者が確認したChatworkテスト用アカウント・ルーム。関連: Issue #5、#6、#9、#12、P11・P12・P18A〜P21。前提となる詳細は `chatwork-report-delivery-implementation-plan-2026-11-02.md` を参照する。

本書は**実装・実環境テストの指示書であり、合格記録ではない**。実務の `report_approved=0`・`DeliveryEnabled=false` を維持し、試験で許可された報告だけを同じ配送基盤で扱う。利用者が確認したテストルームでも、個人情報を含まない試験データだけを投稿する。秘密値・room ID・投稿ID・職員ID・本文は公開Issueに載せず、非公開証跡と突き合わせる。

## 現在の接続状態と障害（2026-11-02〜03の作成当時の記録）

以下は作成当時の観測であり、現在の配備状況を示さない。後続の進捗記録とIssue #12を参照し、実環境の最新状態は都度確認する。

1. ローカルには許可行の不変制約、確保・取消・期限切れの一部、運用者による取消、認証済み監視による期限切れ処理がある。実D1・公開Siteへ未配備。許可発行・職員による試験登録・成果物API・報告ワーカー・結果不明の照合は未接続。
2. 既存の試験許可テーブルは既存ジョブIDを必須とし、既存の通常報告ジョブ作成は `report_approved=1` を必要とする。このままでは実務を無効のまま試験ジョブを作れない。また、監視・claim・dispatch-recordは現状確認投稿のみを配送対象とする。試験用の登録と配送対象判定を実装する必要がある。
3. OAuthの現行要求には `rooms.files:write` がない。アプリの画像受付は8,000,000バイトまでだが、ChatworkのファイルAPIは5 MB上限。権限追加の具体的な内容・参加ルームへの影響は実施時に利用者に示し、承認後に再認可する。上限超過は初回外部POST前に検出して表示し、無断圧縮・分割しない。
4. 直近の観測ではGoogle Cloud CLIのトークン取得がタイムアウト。原因と、途中で中断した実行主体の作成結果は不明。再認証を含む切り分けの前に成否を推測して再作成しない。
5. 実装者は現在の未コミット差分と別ツリーの画面修正を保全し、同一Site・同一D1を対象としているか確認する。ローカル版の成功、以前の確認投稿成功、別環境の試験は実報告配送の合格ではない。

## 実装する接続の形

### A. 試験許可の発行とジョブの循環解消

- [ ] **C01 設計・モード固定**: ジョブにサーバー管理の `test`／`production` 区分を永続化し、不変にする。通常ジョブは従来の実務承認を必須とし、試験ジョブには別の有効な試験許可を必須とする。クライアントの文字列やリクエスト値だけでモード変更できない。DB移行、既存ジョブの扱い、監査、同時更新を先にテストする。実務への反映前に仕様・設計レビューを行う。
- [ ] **C02 許可前のデータ**: 有効な現場職員が、個人情報のないテスト作業を保存し、Markdown報告版を確定する。この時点で外部送信しない。現場職員は自分の報告版のみ使用する。テスト対象と確認した証跡を非公開に保持し、任意の既存実データを一括で試験対象にしない。
- [ ] **C03 認証付き運用者発行**: C02で固定した報告版・作成者・検証済みアカウント／ルームを運用者が非公開管理面で照合。認証・監査付き操作で、DB上に配送不能な試験専用の予約ジョブと許可を一体で作る方式を実装する。具体的には、同一D1 batch内でジョブを `TestAwaitingRegistration` として作成し、そのジョブIDに紐づく許可と監査を作成する。中間失敗・条件不一致・一意制約違反では全部ロールバックし、片方だけの行を残さない。通常の `createReportDelivery` に一時的な実務承認を与えない。
- [ ] **C04 許可に固定する値**: 許可ID、1報告版・1ジョブ、作成者・職員版、固定アカウント・テストルーム・設定版、Site版、worker主体・revision・digest・承認世代、DB時刻で判定する期限、試験登録回数上限、運用者・理由・監査を保存する。実行版はCloud Run実配備と承認監査の両方を照合し、ワーカー自己申告の文字列だけを信用しない。試験回数は**1許可につき1ジョブ**とし、複数成果物をその1ジョブ内で順番に送る。同一要求の再送は同じ予約を返し、別の報告・ジョブに許可を流用できない。別の試験には前の試験の全結果と必要な隔離を解決したうえで新しい許可を発行する。
- [ ] **C05 発行APIの認可と冪等性**: 既存の運用者専用認証・CSRF／サービス境界を使い、要求は報告ID・対象識別・期待世代・期限・理由・発行要求ID等に限定。サーバーがDBと承認監査から送信先・主体・版を解決し、本文・添付・R2 keyや任意URLを受け取らない。発行要求IDで応答喪失を再試行しても同じ許可と監査に収束。期限超過、既存ジョブ／別要求ID競合、未承認Site・worker、古い設定版、職員降格、ルーム変更、無認証、トークン未接続、上限不正は拒否。許可と固定値の後変更、取消後再有効化、監査行なしの成功を防ぐ。運用者以外・ワーカー秘密値のみで発行できないことをHTTP・DB試験で確認。
- [ ] **C06 職員の明示的登録**: 作成者本人かつ有効な現場職員だけが、試験許可・期限・上限・固定された報告版と送信先・職員版・配備版・承認世代・正常heartbeatを確認し、画面で「試験送信」と明示して登録できる。本人による登録の前に、運用者発行の予約ジョブはmonitorから見えず、Tasksを作らず、外部投稿しない。登録APIは任意の本文・room・添付keyを受け取らない。
- [ ] **C07 登録と一覧封印**: 許可、職員、設定、期限、予約状態と登録回数をDBで検証し、報告snapshotから本文・Markdown・画像・PDFの完成済み成果物一覧を原子的に保存・封印してから、試験ジョブを配送可能状態にする。現行のジョブ作成と一覧封印が別batchである点は解消するか、未封印を送れないまま同じ予約を安全に再試行できる方式を実装する。回数確保・重複要求・応答喪失・同時登録を競合試験し、失敗時に不完全一覧や余分なジョブを残さない。未封印で職員版が変わった場合は、未投入・未リース・投稿IDなし・成果物行なしを証明した場合だけ条件付き失効し、新しい報告版へ進める。証明できない場合は保留。
- [ ] **C08 試験外の拒否**: 他職員・通常職員・他報告版・他ルーム・別アカウント・古い職員版／設定版・期限切れ・上限超過・取消済み・旧配備主体・無認証は各段階で拒否。試験許可で実務用送信登録や他ジョブの通常確保を通さない。`report_approved=0` と `DeliveryEnabled=false` を試験前・試験中・後片付け後に確認する。

### B. 成果物とworkerの接続

- [ ] **C09 成果物確定**: 報告本文・Markdown・画像入りPDF・画像は確定済みsnapshotに基づき固定し、完了した一覧のみ封印する。画像の所属作業、重複、R2の存在・MIME・内容・サイズ、生成済みPDFの日本語・画像・ページ・容量を確認。Chatwork制限の境界を公式仕様・実環境で確認し、成果物が上限を超える場合は**本文を含めどれもPOSTする前**に理由と復旧方法を表示する。失敗・削除・変更中に別版の画像を混ぜない。
- [ ] **C10 monitorとTasks**: 登録済みかつ許可された封印済み試験ジョブのみmonitor対象にする。タスク本文にはジョブID等の最小識別子だけを入れ、報告本文・添付・トークン・room IDを入れない。記録名がなければ決定的な初回名を照会し、存在を確認できたら再作成せず、不存在を確認したときだけ新しい試行名を使う。作成時409後も実在を照合し、権限エラー／照会失敗は成功扱いしない。期限・取消・設定変更・旧主体・認証失敗では投入・確保を拒否し、同時monitor／タスク重複では単一確保にする。
- [ ] **C11 内部API**: 専用workerの共有秘密値とGoogle OIDCの検証、主体・audience・世代・Site／worker版・実配備digestの承認、許可の固定対象とDB時刻期限、現場職員版、ジョブ・成果物リースをDB変更条件で検証。試験ジョブ用に成果物の順次確保、対象本文・限定R2取得、短期アクセストークン取得、結果保存を接続する。通常経路のAPIでは試験許可や `report_approved=0` を迂回できない。取消と競合する旧主体の更新、他ジョブの成果物、別workのR2 key、期限外の読み取りを拒否。
- [ ] **C12 送信**: workerは確保済み成果物からのみ固定宛先へ送信する。本文はmessages API、Markdown・PDF・画像はfiles APIのmultipart送信を使用。ファイルAPIの `file_id` とメッセージAPIの `message_id` は種類別に保持し、レスポンス仕様とChatwork画面を照合する。必要なアクセストークンは短期メモリで扱い、ログ・Tasks・永続領域・Issueに残さない。更新トークンはSiteから出さない。
- [ ] **C13 完了と部分失敗**: 各成果物の成功・確定失敗・Unknownと対応IDを保存し、必須成果物すべてが成功確定したときだけジョブをSentにする。本文送信後のファイル失敗、成功応答の保存失敗、設定／権限変更、失効、429、POST応答喪失では既投稿のIDと元宛先を保持し、残りを保留。通信エラーや曖昧な応答を未送信と決めつけず、Unknownを自動再送しない。
- [ ] **C14 POST境界**: 限定許可の取消／期限切れと各成果物の投稿準備確保を、DB状態・世代とDB時刻を使う条件付き更新で直列化。確保より先の取消／期限切れなら確保とPOSTを拒否。確保後は外部POSTの前で停止していても後から投稿し得るため、取消・期限切れでUnknownへ移し、旧試行の結果を安全な条件で記録できなければUnknownを維持する。事前チェックやリース期限だけで未送信と確定しない。認証主体・世代の条件を更新SQL自体に含める。
- [ ] **C15 画面と終了**: 作成者に試験送信・固定ルーム・報告版・添付・状態を表示。履歴は本人に限定し、Pending／Posting／Sent／Failed／Unknown・部分送信を区別する。取消・期限切れ後は新規登録と未確保の送信を止める。処理中・Unknownは勝手に消さず、結果と監査を保持する。実務ボタンは有効化しない。

### C. Unknownの隔離・照合・再試行

- [ ] **C16 対象固定と取得**: 旧試行のジョブ・成果物・元アカウント／ルーム・一意識別子・発行済み投稿ID・許可／承認世代と状態を権限付き画面／APIで固定。部分送信済みと未確認分を区別し、異なるルームへ自動切替しない。
- [ ] **C17 旧試行の隔離**: 実行担当が旧worker主体の承認を取り消し、旧Cloud Run処理の停止・再開不能・実行中HTTP終了、旧アクセストークンと更新トークンが新規POSTに使えないことを、P12の有効期限前後対照で実証する。取得済み同一トークンの移送は独立検証器の一時メモリに限り、秘密を永続化・ログ出力しない。トークンの自然期限切れ、権限喪失、通信障害を失効成功と誤判定しない。証明できなければUnknownを維持する。
- [ ] **C18 監査付き照合**: 隔離の証拠参照、停止・無効化・処理中要求終了の各確認、対象成果物、確認者、理由、照合時刻を運用者認証付きAPIで保存し、旧形式の記録を代用しない。送信済みと確認した場合は対応するChatwork IDを記録。未送信と確定するにはC17に加え実ルームを独立に照合し、確認不能・矛盾はUnknownのまま。処理中の複数職員・取消・古い世代・同時照合をDB競合テストし、監査と状態更新を原子的に行う。
- [ ] **C19 新試行**: 未送信確定後も旧ジョブ・旧ID・監査は保持。同一report IDの一意制約を削除・流用せず、新しい報告版・新しい試験許可として発行する。旧主体が新しい資格情報・新主体へアクセスできないことを確認し、テストアカウント再認可・新主体承認・heartbeat後にだけ試行する。期限切れ・POST未観測・リース満了のみでは再試行不可。
